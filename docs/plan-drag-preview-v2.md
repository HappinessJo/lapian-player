## 1. 为什么要再做一轮

`079f0dd` 解决了“快速拖动时整段冻住”：不再每个鼠标事件中断解码，正向
连续发布中间帧，反向允许粗帧。`media\测试.mp4` 快拖 +60 帧/16ms 从
28.6fps/空档 93.8ms 提升到约 **60fps/32ms**。

但用户实测仍反馈：

1. **超大幅度**拖动仍不能“随心所欲”；
2. **反向拉进度条**明显更卡；
3. 对比电影与电视、AE（缓存好时）仍有差距。

根因不是上一轮没修好，而是上一轮只解决了“不中断”，没有解决
“**当前显示帧与鼠标目标帧的差距**”和“**反向 seek 成本**”。

### 1.1 一个必须纠正的指标

当前 `--drag-fast` 测的是 **Present fps** 和**最大呈现空档**，不是
“显示帧 == 目标帧”。+60 帧/16ms 意味着目标每秒前进约 2 秒内容；
软件解码不可能真的按这个速度解出对应内容。60fps 只能说明“画面在动”，
不能说明“画面跟到了鼠标位置”。

因此 DP 计划必须新增：

- `target_lag_frames` / `target_lag_ms`：每次 Present 时，显示帧号与
  当前拖动目标的差；
- `first_coarse_ms`：远跳后第一张粗帧的时间；
- `settle_exact_ms`：松手后精确到帧的时间（沿用 P6）；
- `cache_hit_rate`、`seeks_per_second`、`hw_active`。

没有这些，继续追求 fps 会得到“看起来 60fps、实际内容落后几秒”的假象。

## 2. 现状架构

```
MainWindow（UI 线程）
  ├─ 主播放：MediaSession + 硬件 VideoDecoder → GfxWidget/VideoRenderer
  └─ 拖动预览：PreviewDecoder（独立线程，软件 VideoDecoder）
        seek 关键帧 → 向前解码 → sws 缩到 ≤1280 NV12
        → 32 帧缓存 → TakeLatestFrame → GfxWidget
```

关键事实：

| 项 | 现状 |
|---|---|
| 主播放解码 | 共享 D3D11 设备，硬解可用 |
| 预览解码 | `decoder.Open(..., prefer_hardware=false)`，**软件** |
| 预览缩放 | CPU `sws_scale` 到最长边 1280 |
| 预览缓存 | 32 帧（约 44MB @720p NV12） |
| 反向 | 不能倒放；每个新目标 seek 到更早关键帧再向前解 |
| 预览与 UI | 单预览线程；UI 16ms 取最新帧 |
| 目标语义 | 拖动中近似；松手 `GoToFrame` 精确 |

`media\测试.mp4`：1080p H.264 30fps、4573 帧、GOP 30 帧（1s）。

| 测量 | 数值 |
|---|---|
| 软件 seek | p50 26.5ms / p95 **77.9ms** |
| 硬件 seek | p50 12.8ms / p95 **29.4ms** |
| 60fps 预算 | 16.7ms/帧 |
| 当前快拖 +60 | 60.0–61.0fps / 空档 32ms |
| 当前反向 -60 | 42.7fps / 空档 48.5ms |
| 当前反向 -20 | 11.5fps / 空档 191.8ms |
| 普通 P6 松手 | 17.1ms |

**结论**：软件预览每次 seek 的 p95 已超过 60Hz 一帧的 4 倍；反向每步都
可能 seek，所以反向必然比正向差。仅靠参数调整无法跨越这个物理限制。

## 3. 目标与非目标

### 目标

1. 1080p 本地视频快拖**不再整段冻住**；正向、反向都有持续画面。
2. 快拖时优先“跟随目标”而不是“精确解码”：显示最近可用帧/粗帧；
   松手仍精确到帧。
3. 反向明显改善：已解过的区域优先命中缓存，远跳先出粗帧。
4. 硬件预览可用时优先硬解；失败自动回退软件，不黑屏、不崩溃。
5. 预览缓存有硬上限，不把内存/显存拖垮。
6. 所有改动可单独回退；不改主播放、在线缓存、记录、M1/M2/P4/P7。

### 非目标

- 不做全片逐帧缓存（1080p 30fps 2h ≈ 670GB，不可能）。
- 不承诺拖动中每一帧都等于鼠标目标；只承诺“有画面、尽快接近、松手精确”。
- 不承诺 4K/HEVC/AV1 任意拖动通过；4K 只记录，不设门。
- 不改 `OnlinePreviewDecoder`/T8.6.1b 语义；在线预览仍走现有路径。
- 不改 `lapian-cache-1` schema、OB 样本、默认 AVC≤1080p、M1/M2 门。
- 不引入新播放器/新框架/外部服务。

## 4. 目标架构

```
MainWindow 拖动事件
  → PreviewController（策略：快拖/慢拖/反向/松手）
      → PreviewSource（硬件优先，软件回退）
          → PreviewRingCache（播放头附近双向帧缓存）
          → KeyframeThumbnails（远跳粗帧，低分辨率、滑动窗口）
      → Present 最近可用帧
  → 松手：停止预览，GoToFrame 精确
```

三层职责：

1. **Exact/near**：硬件解码 + 环形缓存，覆盖播放头附近和刚拖过的区域。
2. **Coarse/far**：关键帧缩略图/最近粗帧，远跳先给画面，不空等。
3. **Settle**：松手后精确解码；不把“粗帧”当最终结果。

### 4.1 硬件预览

- `PreviewDecoder::Configure` 增加可选的 `ID3D11Device*`（借用或
  `ComPtr` 持有；生命周期由 MainWindow 保证）。
- 预览线程优先 `VideoDecoder::OpenWithD3D11Device(..., prefer_hardware=true)`；
  失败回退 `Open(..., false)`。
- 硬件帧不经过 `sws_scale`，直接交给 `VideoRenderer`（现有
  `UploadHardwareFrame` 已支持同设备纹理）；软件帧仍走现有缩放。
- 缓存策略：DP-1 不扩大缓存；硬件帧缓存先关闭或只保留少量，避免显存
  被 32 帧纹理占满；DP-2 再统一做缓存预算。
- 失败/设备不匹配/黑帧：立即回退软件，记录 `preview_hw_fallback` 原因；
  不允许“假 hw=1”。

### 4.2 反向缓存/预取

- 新增有界 `PreviewRingCache`（建议总预算 **≤256MB**，可配置）：
  - 保存最近解码的预览帧（软件 NV12 或同设备硬件帧）；
  - 反向目标先查缓存，命中直接发布；
  - 未命中：seek 到目标前关键帧，向前解码，填缓存。
- 播放头附近预取：
  - 空闲时预解当前 GOP / 上一 GOP 的若干帧；
  - 反向拖动优先命中已预取帧；
  - 预取可取消，不能阻塞当前目标。
- 远跳粗帧：
  - 低分辨率关键帧缩略图（建议 320×180，滑动窗口 + LRU，预算 ≤64MB）；
  - 远跳先发最近缩略图，再后台解精确帧；
  - 不承诺缩略图是目标帧，只承诺“先有画面”。
- 不允许无界缓存；淘汰按帧号距离 + LRU。

### 4.3 交互策略

- **慢拖/小步**：优先精确目标帧（现有语义）。
- **快拖/大跳**：优先最近缓存/缩略图；允许目标滞后；不阻塞 UI。
- **反向**：缓存命中优先；未命中先粗帧，再精确。
- **松手**：停止预览，`GoToFrame` 精确；P6 目标 ≤150ms 不变。
- **模式切换**：按目标变化速度/距离判定，不按“感觉”；阈值写入诊断日志。

## 5. 指标与验收

### 5.1 新增指标

| 指标 | 含义 | 目标 |
|---|---|---|
| `present_fps` | 实际 Present 帧率 | 不低于现行 P4（≥30） |
| `max_present_gap_ms` | 相邻 Present 最大空档 | 正向 ≤50ms；反向 ≤80ms（DP-2 后 ≤60ms） |
| `target_lag_ms` | 显示帧相对当前目标的滞后 | 慢拖 ≤2 帧；快拖记录 p50/p95，不设硬门 |
| `first_coarse_ms` | 远跳后第一张粗帧 | ≤100ms |
| `settle_exact_ms` | 松手精确到帧 | ≤150ms（P6 不变） |
| `cache_hit_rate` | 反向/局部拖动命中率 | 记录并逐步提高 |
| `hw_active` | 预览是否真硬解 | DP-1 在开发机必须为 1；回退时明确记录 |
| 内存/显存 | 预览缓存峰值 | ≤256MB（另缩略图 ≤64MB） |

### 5.2 体验目标（非门）

以 `media\测试.mp4` 为基准：

- 正向快拖 +60/+120/+300 帧/16ms：**不冻住**，fps 不低于 `079f0dd`
  （约 60fps），最大空档 ≤50ms；
- 反向 -60：fps ≥45、最大空档 ≤60ms（DP-2 目标）；
- 反向 -20：从 11.5fps 提升到 ≥25fps（DP-2 目标；达不到则记录残余）；
- 远跳：首张粗帧 ≤100ms，松手精确 ≤150ms；
- 4K/HEVC：只记录，不设通过线。

这些是**体验目标**，不是 spec/P4 验收值；不得写成 MVP 通过。

## 6. 任务拆分

### DP-0 规划（本会话完成）

- 产出本文件、任务表、交接、下一会话提示词。
- 不改代码。

### DP-1 硬件预览 + 诊断

**范围**：`PreviewDecoder`、`MainWindow` 设备传递、`GfxWidget` 设备生命周期、
`--drag-fast` 诊断；不改缓存策略。

**验收**：
- 开发机硬件预览 `hw_active=1`；软件回退可强制验证；
- 1080p 快拖不低于 `079f0dd`（正向约 60fps/≤50ms；反向 -60 ≥42fps/≤80ms）；
- 无黑帧、无崩溃、无设备丢失；T8.6.1b/本地播放不退化；
- `ctest` 36/36、key 77/0。

### DP-2 反向缓存 + 预取 + 远跳粗帧

**范围**：`PreviewRingCache`、预取、关键帧缩略图；内存/显存预算。

**验收**：
- 反向 -60 ≥45fps/≤60ms；反向 -20 ≥25fps；
- 反向局部拖动缓存命中率 ≥70%（记录口径）；
- 远跳首张粗帧 ≤100ms；
- 预览缓存峰值 ≤256MB，缩略图 ≤64MB；
- 不影响主播放内存/在线会话。

### DP-3 交互策略 + 验收探针

**范围**：快拖/慢拖/反向/远跳策略，`target_lag` 探针，`--drag-fast` 输出扩展，
`PreviewDiagnosticsForTest`。

**验收**：
- 慢拖目标滞后 ≤2 帧；松手 P6 ≤150ms；
- 快拖不冻住，最大空档达标；
- 远跳先粗后精；粗帧不被误当最终帧；
- 诊断能区分“精确帧/粗帧/缓存命中/硬解”。

**完成记录（2026-10-24）**：四模式 `Exact/Fast/Reverse/FarJump`
（阈值 4/300 帧，含方向/间隔/同向次数/速度）；Exact 关闭粗帧；
FarJump 用 `deferred_exact` 保证先粗后精，并禁止精确目标后的粗帧替换；
`PreviewTestDiagnostics` 增加 mode/lag/cache_hit_rate/displayed_hardware；
新增 `--drag-strategy-test`。慢拖 +1/-1 lag p95=0（15.6ms 节奏 ≤2）、
远跳粗帧 20.8/20.6ms、精确 30.6/30.0ms、P6 p95 18.8ms；
`ctest` 37/37、key 77/0、T8.6.1b 35/0。证据
[perf/drag-preview-dp3.md](perf/drag-preview-dp3.md)、交接
[handoff-2026-10-24-dp3.md](handoff-2026-10-24-dp3.md)。

## 7. 风险与回滚

| 风险 | 处理 |
|---|---|
| 共享 D3D11 设备导致黑帧/崩溃 | DP-1 先 spike；失败回退软件；保留 `--preview-force-software` |
| 硬件帧缓存占满显存 | DP-1 不缓存硬件帧；DP-2 统一预算、LRU |
| 反向粗帧向前跳 | 继续用 `last_delivered` 单调约束；不满足则丢弃 |
| 预取阻塞当前目标 | 预取可取消、低优先级；主目标优先 |
| 内存超预算 | 硬上限 + 统计；超限淘汰，不增长 |
| 4K/HEVC 仍不达标 | 记录，不设门；不写“4K 通过” |
| 主播放退化 | 预览路径隔离；任何主播放/在线回归即回滚 DP 改动 |

## 8. 决策记录

- DP-1 先做硬件预览，DP-2 再做缓存/预取；不先堆缓存掩盖软解瓶颈。
- 预览缓存有界，不做全片缓存；远跳用缩略图，不空等。
- 拖动中允许近似；松手必须精确；不改 P4/P6 数字。
- 1080p 先达标；4K best-effort，只记录。
- DP 任务独立于 `tasks-v2.md`，不混入 v2 在线任务；不新增门。
- 不改 `OnlinePreviewDecoder`；在线预览仍由 T8.6.1b 负责。
