# 拉片软件 v2 产品愿景：B 站在线拉片

- **版本**：v1.1（2026-10-23 DEC-6：扫码登录并入 MVP 增强）
- **状态**：已拍板。S1 产品定义产出；五个决定由用户逐条确认；**DEC-6 把“扫码登录”从“明确不做”改为“MVP 增强（T8.2.2，非门）”**。
- **依据**：[AGENTS.md](../AGENTS.md) v6.7、[spec.md](../spec.md) v0.3、[product-v2-bilibili-proposal.md](product-v2-bilibili-proposal.md)、[tasks.md](../tasks.md) v0.28
- **范围**：只回答"为什么做、给谁做、做到哪、怎么算成功"。**不含实现方案**；架构、验收口径、任务拆分在 S2/S3 产出，不在此文承诺。

---

## 一句话

给 MAD/PV 作者的**在线逐帧研究工具**：贴一个 BV 号，几秒开始播，边看边缓存，用帧号、波形、循环、标记、截图把片子拆开看；本地文件播放保持 v1 的全部能力。

它不是 B 站下载器，也不是网页播放器加逐帧键。差异化仍是 v1 那三件事：帧号可直接输入、波形与画面共用一根帧级时间轴、打开即用零项目——只是入口从"已有文件"变成"一条链接"。

---

## 1. 目标用户

**第一用户：静止系 MAD 作者**（含 PV 作者）。

- 真实场景：在 B 站刷到一条想研究的 MAD，想知道"这个转场是怎么切的、这一拍的画面踩没踩在鼓点上、这段运动用了多少帧"。现在只能下载再丢进 AE 拖时间轴。
- 他要的不是"看视频"，是"把 2–4 分钟的片子拆成一百个可回访的帧"。
- 判据很硬：**如果在线模式不能省掉"下载 + 导入 AE"这两步，他不会用。** 这也是全部指标的由来。

**第二用户**：MG 动画师、动画师。诉求高度重叠，功能对他们同样可用；但默认交互与验收优先服务 MAD/PV 的"卡点 + 逐帧看转场"。

**不服务的用户**：只想把视频看完的人（用 B 站客户端）、想收藏/批量存片的人（用下载器）、要剪辑的人（用 AE/PR）。

---

## 2. 核心工作流

**主路径（P0，任何一步被阻断即产品不成立）**

1. 在 B 站找到一条 MAD，复制 BV 号或链接。
2. 贴进拉片软件，几秒内起播。
3. 看波形找卡点 → 拖到那一帧 → PgUp/PgDn 逐帧确认切点。
4. 设 A/B 循环，0.25–0.5x 反复看一段运动，再逐帧看形变。
5. 在关键帧打标记、写一句备注、截一张图。
6. 关掉；下次再贴同一个 BV，标记/备注/截图还在，不重新联网。

**分支（必须可预期，不能崩）**

- 拖到未缓存区域：明确显示"缓冲中"，取到后继续。**不假装瞬时**。
- 网络中断：保留已缓存部分，可重试，标记不丢。
- 打不开（BV 无效 / 需登录 / 地区限制 / 付费 / DRM / 磁盘不足 / 解析失败）：5 秒内给出可读原因与下一步。

**本地路径（P0，不得退化）**：`Ctrl+O` / 拖拽 / 文件关联打开本地文件，**零网络**，能力与 v1 完全一致。

## 3. MVP 范围

**做**

- **输入与解析**：BV 号或 URL；显示标题、作者、时长、可用清晰度。
- **在线播放**：缓冲阈值起播、缓冲区间可见、取消、重试。
- **已缓存区域**：逐帧、seek、波形、标记、备注、截图，全部沿用 v1 交互与键位。
- **缓存**：自动落盘；占用可见；配额 20GB；LRU 淘汰；可手动清空；**缓存命中时不联网直接打开**。
- **清晰度**：默认按"保帧率优先"自动选档，用户可手动切档。
- **凭据**：可选；**粘贴 SESSDATA** 与**扫码登录（T8.2.2，非门）**两种方式**长期并存**（粘贴不是过渡），本地加密、可一键清除，用于提升到登录可见档。扫码失败/无手机/风控时回退粘贴。
- **错误与降级**：§2 分支里每一条都给可读提示，不冻结。
- **本地模式**：保持零网络、不动 v1 性能口径。

**不做（MVP 内明确不做）**

- 显式"下载 / 离线缓存"按钮与下载进度条——这与"无下载步骤"的在线语义冲突。
- 搜索、推荐、排行榜、收藏夹、批量导入。
- 弹幕、评论、字幕、多音轨切换。
- 账号体系（注册/个人主页）、多账号切换、云同步。<!-- DEC-6：扫码登录移出“不做”，作为 MVP 增强 T8.2.2（非门） -->
- 缓存导出、分享、把缓存当视频文件另作他用。
- 后台预取其他视频（只缓冲当前正在看的这一条）。

---

## 4. 非目标

- **不做 B 站下载器/第三方客户端。** 核心仍是"逐帧研究"，不是"收藏与下载"。
- **不承诺"任意帧即时、完全不缓存"。** 在线一定缓冲，帧级研究一定落盘。
- **不绕过付费 / DRM / 地区限制。** 无凭据不取付费内容；不做代理、伪装 IP、改 header 骗地域；不做共享账号或账号轮换。
- **不承诺在线 4K/HDR 的性能与颜色。** 这些档一律按"可用档"呈现。
- **不改变本地模式。** 零网络、P1/P2/P7 不退化。
- **不跨平台。** 仍是 Windows 10 21H2+ / 11 x64。
- **不一次规划完"完整品"。** 先闭环 `BV → 在线 → 逐帧 → 记录`。

## 5. 五个决定

| # | 议题 | 结论 | 理由 / 代价 |
|---|---|---|---|
| 1 | **在线语义** | 接受"几秒起播、边看边缓存、已缓存区域逐帧、未缓存显示缓冲中"；接受"缓存落盘但无显式下载步骤"，且**缓存可见、可清、可配配额**。 | 帧级 seek/波形/索引都需要本地字节，"不落盘"不存在。把缓存做成可管理的事实，比假装没有更诚实。代价：P7 ≤80ms **只在已缓存区间承诺**，缓冲区边界外不承诺。 |
| 2 | **登录 / Cookie** | MVP 支持**用户自带 Cookie**：粘贴 SESSDATA 或**扫码登录（T8.2.2，非门）**，本地加密、可退出清除；**不做账号体系（注册/个人主页）、不做账号密码、不做多账号**。未登录仍可用，但明确提示清晰度受限。 | 匿名访问的实际清晰度大概率只到 480p，MAD 的转场/形变细节会被压缩毁掉，工具会失去意义。**DEC-6（2026-10-23）**：用户要求“傻瓜化”，把扫码登录并入 MVP 增强——只走 B 站官方网页二维码流程、本地渲染、只保留 SESSDATA；不引入 WebView/账号密码/多账号，扫码失败回退粘贴。代价：新增 `passport.bilibili.com` 白名单、约 1–1.5 天实现、一次真实扫码证据；**非 M1/M2 门**。 |
| 3 | **清晰度与缓存** | **保帧率优先**：有 60fps 档时优先 1080P60 → 720P60；**拿不到 60fps 档时退为 1080P30 → 720P30 → 480P，并强提示"帧率已降，帧号与源片不同步"**。默认只选 H.264。**配额 20GB + LRU 自动淘汰 + 可改可清空**。 | S2 实测（普通用户、非大会员）：**拿不到 1080P60，也拿不到 4K**，60fps 素材最高只有 1080P@29.4。所以"保帧率"只在有 60fps 权限时成立，其余情况必须把"帧号不可与源片对齐"写在脸上。20GB ≈ 5.6–6.8 小时 1080p（AVC 2.1–2.6Mbps）。 |
| 4 | **合规边界** | **不绕过**（不做无凭据取付费、不做地区伪装）是红线；在红线内**凭据能给到的最高档全开，含 4K**，但一律标"可用档：性能不保证、颜色不保证"。 | 用户用自己的权益不是绕过；但 4K/HDR 在 v1 里是可用档、HDR 明确不保证颜色（spec §4.2），不能因为"能取到"就变成承诺。**S2 实测**：普通用户拿不到 4K，也拿不到 1080P60；4K 档目前只存在于大会员侧（未测）。**口径**：默认仍选 H.264；4K 档允许 HEVC/AV1。 |
| 5 | **成功指标** | 主指标 = **任务完成率**。起播时间是入口闸门；已缓存区步进是体验门槛；缓冲次数只做诊断。 | 这个产品的对手不是 PotPlayer，是"下载 + 丢进 AE"。唯一能证明它成立的是**用户不再回退去下载**。只测起播或只测步进，都测不出"能不能干完活"。 |

## 6. 成功指标

**主指标：任务完成率**

> 定义：一次会话内"输入 BV → 起播 → 至少一次实质逐帧研究（≥10 次 PgUp/PgDn，或一次 A/B 循环慢放）→ 至少一次标记或截图"，**且中途没有退出改去下载、没有换工具重来**的比例。

- 目标（草案，S3 用真实数据定）：自用 + 3–5 位目标用户试用中 **≥80%**；"回退到下载 + AE" **≤1/10 次**。

**闸门（任一不达标，MVP 不算成立）**

- 起播：良好网络、1080P 档，**p95 ≤5s**。
- 已缓存区域 PgUp/PgDn：沿用 v1 P7（1080p ≤80ms p95）。
- 本地模式 P1 / P2 / P7 不退化。

**诊断（只记录，不作为承诺）**

- 缓冲次数与单次缓冲时长；完整看一条 MAD 期间 >1s 的卡顿次数。
- 实际落档分布（多少条落到 480p / 720p / 1080P30 / 1080P60 / 4K）。
- 缓存命中率；Cookie 失效需重贴的频率；**扫码登录成功率与失败回退率**；错误提示后的重试成功率。

**反指标（变坏就是做错了）**

- 缓存占用超过配额、用户开始手动删目录。
- 本地模式出现任何网络请求。
- 为追清晰度而牺牲帧率一致性。

## 7. 风险

| 风险 | 影响 | 产品层面应对 |
|---|---|---|
| **P7 承诺落差** | 用户在未缓存边界按 PgUp 会等，和 v1 的"80ms"心智冲突 | UI 区分"已缓存/缓冲中"；边界外不承诺数字；首次使用明确说明 |
| **60fps 片源降帧** | 帧号与源片不同步，逐帧研究失真 | S2 实测：普通用户最高只有 1080P@29.4，**没有 60fps 档**。降帧必须强提示"帧号约为源片 1/2，不保证逐帧对应"，不能只提示"清晰度受限"；标记/截图元数据记录 fps。 |
| **4K 只有 HEVC/AV1** | 与"默认只选 H.264"冲突；硬解/帧精确/内存都未验收 | 4K 只作可用档；默认档仍走 H.264；S2 必须实测各档实际编码 |
| **B 站接口/签名/CDN 变化** | 解析或取流突然失效 | 解析层与播放层解耦、可独立更新、失败给可读提示；不把"能用"当作长期承诺 |
| **风控/限频** | 请求被拒或账号受限 | 单用户、低频、只响应用户主动输入、不做后台预取与批量；失败退避 |
| **Cookie 安全与失效** | 凭据泄露或反复失效 | 本地加密存储、明示用途、一键清除、不进日志；失效给明确引导而非静默降档 |
| **缓存配额与磁盘** | 20GB 被吃满或磁盘不足 | 配额可见、LRU 自动淘汰、开播前检查空间、不足时先提示再降级 |
| **断网与 URL 过期** | 播到一半断流、花屏 | 保留已缓存数据、可重试、标记不丢；不崩溃 |
| **索引/波形不完整** | 总帧数、波形与本地不一致 | 沿用 v1 三态（扫描中/≈/精确）与"波形生成中"；未完成不承诺精确 |
| **合规与 ToS** | 上线/分发风险 | 不绕过、不再分发缓存、不批量；发布前评审；明确"仅个人研究" |
| **范围膨胀** | 从"逐帧研究"变成"B 站客户端" | 本文 §3/§4 的非目标是硬边界；新想法进候选池，不进 MVP |

## 8. 留给 S2 spike 的问题（本文不定）

1. 匿名 / 普通登录 / 大会员三档，**各自实际能拿到哪些清晰度与编码**？（决定 Q3 的回退顺序是否命中真实档位，也决定 4K 是否真能取到）
2. 4K 是否只有 HEVC/AV1？如果是，默认 H.264 与"4K 全开"如何共存——当前口径是"默认 AVC，4K 档允许 HEVC/AV1 并标可用档"。
3. 已缓存边界外 PgUp/PgDn 的真实等待时间分布（决定要不要做跨边界自动预取）。
4. "缓存命中后完全不联网打开"是否成立（决定"下次再看同一条"这个高频动作能不能兑现）。
5. 断网 / URL 过期 / 缓存损坏时的最小可恢复行为。

## 附：与 v1 的关系

- v1 的全部能力、键位、sidecar、截图、性能口径**不变**，作为"本地模式"整体保留。
- 本地模式**零网络**是 v1 的承诺，v2 不得破坏；在线模式只在用户主动输入 BV/URL 后才联网。
- `spec.md` v0.3 仍是本地模式的验收依据；在线模式的验收口径由 S3 的新版本记录追加，**不静默修改 v0.3**。
