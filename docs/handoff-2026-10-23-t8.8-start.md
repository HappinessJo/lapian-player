## 2. 先复核一个关键线索：OB-2 可能不是外部 blocked

T8.5 的结论是“OB-2 只给 360P”，但请求参数与 S2 的 3/3 观测并不完全一致：

- S2 登录档表（[v2-online-spike.md](perf/v2-online-spike.md) §2.2）记录：
  - S-1 `durl qn=120` → **64（720p）**
  - S-2 `durl qn=120` → **80（1080p）**
  - S-3 `durl qn=120` → **64（720p）**
  - 即登录后 3/3 均 ≥720p，是在 **qn=120 + fourk=1** 的请求下观测到的。
- T8.5 产品栈实际请求：
  - `OnlineSession::StartPlayUrlWorker` 固定 `FetchPlayUrl(..., 64, ...)`；
  - `BuildPlayUrlUrl` 将 `fnval=0`、`fourk=0` 写死；
  - `--online-fetch-test` 的 `--qn-1080` 只映射到 **80**，不是 120；
  - T8.5 只记录了 qn=64/80/112 + fourk=0 的 16，没有复现 S2 的 qn=120 + fourk=1。
- **结论**：OB-2 的“360P blocked”可能是**请求档位/`fourk` 参数造成的测量差异**，不能直接当成外部资源限制。T8.8 必须先做参数矩阵，再决定 M1 是否 blocked；**不要沿用 T8.5 的结论直接写 blocked，也不要把 qn=120 的 1080p 当作 M1 已通过**。

### 2.1 T8.8 第一个实验（在改产品前）

用同一份当前 SESSDATA、同一 cid，记录每次的 `request_qn`、`fourk`、服务端 `quality`、`format`、`size`、`durl_count`：

| 请求 | fourk | 目的 |
|---|---|---|
| qn=64 | 0 | 复现 T8.5 的 16 |
| qn=64 | 1 | 判断 `fourk` 是否单独影响 |
| qn=80 | 1 | 最低 1080p 请求是否可得 |
| qn=112 | 1 | 中间档 |
| qn=120 | 1 | 复现 S2 的 80/1080p |

至少对 OB-2 做全矩阵；OB-1/OB-3 做 qn=64/80/120 + fourk=1 对照。禁止打印/提交 SESSDATA、Cookie、签名 URL；只在内存/临时请求里使用。

### 2.2 如果复现 ≥720p

- 做**最小产品改动**：让 M1 的 durl 请求能拿到“可用最高”而不是固定 64。优先只改 `BuildPlayUrlUrl`/`FetchPlayUrl` 的请求参数（可加显式 `fourk` 参数，默认保持旧行为），再改 `OnlineSession` 调用；不要顺手做 DASH。
- 若 `qn=80 + fourk=1` 已能给 OB-2 80，优先用它，避免请求 4K；若只有 `qn=120` 有效，必须记录实际返回，并在产品层加“M1 不超过 1080p”的保护，避免大会员账号意外触发 4K 下载。
- 改完必须重跑 **3/3 真实样本** + 全部 M1 门；不能只用 OB-2 单样本推断 3/3。
- 不得改 M1 门的数字/样本定义；如果实际仍是 2/3，按 blocked 写报告。

### 2.3 如果仍为 2/3

- 这是 **M1 blocked**，不是 T8.8 代码失败；写清楚证据、请求矩阵、实际 qn/分辨率。
- 不要进入 M2，不要用 DASH 结果替代 durl M1，不要改门/数字。
- 给用户三个明确选项，等用户拍板：
  1. 换一条同规格 60fps OB 样本（保留 OB-2 的降帧提示证据，但不计入 3/3 720p）；
  2. 明确接受 durl 2/3 并修改 M1 门（必须走 spec/tasks 版本记录，不能静默改）；
  3. 跳过 M1，直接做 M2 DASH（高风险，需用户明确同意，不能由 agent 自行决定）。

## 3. T8.8 验收清单（按 tasks-v2）

### 3.1 3/3 durl ≥720P

- 3 条 OB（OB-1 `BV1BMnv6jE5S`/42915922022、OB-2 `BV1mA411m7pS`/1004967230、OB-3 `BV1GJ411x7h7`/137649199）。
- 普通用户 SESSDATA 登录；每条实际 `quality >= 64`，下载产物可播、ffprobe 通过；记录实际 qn/format/size/codecid/fps。
- 失败时区分：请求参数、账号权限、接口变动、资源本身只有低档；不要混写。

### 3.2 OP1–OP3、OP5

- **OP1 在线起播**：每条 BV 清该条缓存，20 次确认→首帧；M1 用实际 durl 档（≥720P；OB-2 若 1080p 一并记录），p95 ≤5s，19/20；记录 p50/下行速率。**1080P30 的 OP1 口径留给 M2**，M1 不把 1080p 作为门。
- **OP2 已缓存单帧步进**：实际 durl 档（M1 ≥720P；1080p 口径留 M2），±1，每条 20 次，距缓存边界 ≥2s，p95 ≤80ms。
- **OP3 未缓存 seek**：显示“缓冲中（目标帧 N）”≤100ms；取消 ≤100ms；落点误差 0；进度按剩余字节/速率。
- **OP5 缓存命中**：断网/禁用网络，同一 BV 20 次，p95 ≤2.5s；0 请求；复用 T8.7 的 `CacheHit` 路径与 `--online-offline-test`。

### 3.3 失败矩阵（O1/O7）

至少覆盖：格式不支持、BV 不存在、不可见/私密、未登录、断网/超时、磁盘满、缓存损坏。要求 5s 内可读错误、不崩溃；已缓存区仍可播；记录和缓存不被破坏。

### 3.4 缓存/记录恢复

- 杀进程后同 BV 续传（Range），无重复/损坏字节。
- 清缓存保留在线记录/截图；重建缓存记录回访（T8.7 已单测+E2E，可引用并复跑关键项）。

### 3.5 DEC-5 配额

- 300MB LRU 与 20GB 记账单测按已拍板口径引用；不必真填满 20GB。
- 不把“缓存管理 UI 未做”当 M1 失败。

### 3.6 本地回归 O9

- 零网络（0 TCP/UDP，无 winhttp/wininet/urlmon/Qt6Network）。
- P1 ≤1.5s、P2 ≤2.5s、P7 本地 ≤80ms；至少 `ctest` 全绿、`--robust-test` / 关键本地 E2E 不退化。
- 记录 dist/P12 与内存。

### 3.7 缺陷与 ADR

- 无 P0/P1；已知 P2/P3 写入 T8.8 交接。
- ADR-007 的“附条件接受”评审记录保留，不改 D1–D5。
