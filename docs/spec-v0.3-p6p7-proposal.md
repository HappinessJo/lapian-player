# v0.3 提案：P6/P7/P9 与保证档 GOP 口径

- **状态**：**待用户拍板**；`spec.md` 仍是 v0.2，本文件不修改它。
- **日期**：2026-10-19
- **依据**：[T0.3 真实素材补测](perf/T0.3-seek-probe-real-sample.md)、[T0.3 代理探针](perf/T0.3-seek-probe.md)、[spec.md](../spec.md) §4.1、[plan.md](../plan.md) §4.3/§7 R1
- **目的**：解决“P7 比 P9 更严”的定义冲突，并给长 GOP 一个诚实的性能口径。

## 1. 证据摘要

- 真实 1080p30 H.264，**GOP 30（1s）**：硬解 40 样本 p95 **28.08ms**；P7/P6/P9 下界全过。
- 同一真实内容 **GOP 60（2s）**：硬解 40 样本 p95 **76.06ms**；
  对 P6 150ms / P9 200ms 有余量，对 P7 80ms 只剩 3.94ms。
- 同一真实内容 **GOP 250（8.3s）**：硬解 40 样本 p95 **230.47ms**；
  P7（80ms）、P6（150ms）都超，P9（200ms）也超；落点 40/40 精确。
- 代理 1080p HEVC 60fps GOP 120（2s）：硬解 p95 **63.18ms**，P7/P6 下界通过。
- 代理 4K H.264 30fps GOP 60（2s）：硬解 p95 **258.88ms**；
  P6（300ms）下界通过，P7（150ms）超，P9（200ms）超。
- 以上均为 RTX 4060、冷 seek 探针，不含渲染/呈现；正式验收仍需基线机与 T2.9/T2.10 产品路径。

## 2. 必须先修的定义问题

`spec.md` §4.1 的 P7 是“单帧步进”，P9 是“输入帧号跳转（任意距离）”。
[v0.3 delta](spec-v0.3-delta.md) §6 把 P7 改成“随机距离单步（含 seek，冷/热各测）”，
等于让 P7 覆盖 P9 的场景，而且更严：同一个随机 seek 不可能同时满足 P7 80ms 与 P9 200ms。

**P7 应回到“±1 帧步进”**：PgDn/PgUp/方向键，目标与当前帧相邻；
随机远跳归 P9。这样 P7 靠帧缓存/预取/精确 seek 路径保留帧就能达标，
不再与 P9 冲突。

## 3. 三个方案

### 方案 A（推荐）：GOP 门槛 + 修正 P7

- P7 = ±1 帧步进，不含随机远跳：
  - 1080p ≤80ms p95；4K ≤150ms p95。
  - 以**热解码器 + 帧缓存（精确 seek 路径保留最近 16–24 帧）+ 前向预取**为前提。
  - 跨 GOP 边界的后退步进如果缓存未命中，会退化成一次 seek；2s GOP 的 p95 76.06ms
    对 80ms 只剩 4ms 余量，T2.4 必须专项测这个边界；若超 80ms，把 P7 边界条件收紧到 1s。
- P6/P9 维持强数字，但附带**目标帧距前关键帧 ≤2s** 的条件：
  - 1080p：P6 ≤150ms、P9 ≤200ms（p95）。
  - 4K：P6 ≤300ms、P9 ≤300ms（原 4K 放宽清单漏了 P9，这里补上）。
  - 2s 门槛由真实内容实测 76.06ms 支撑；对 P6/P9 余量足够。
- 超过 2s 的定位仍**帧精确、可播放**，但按“可用档性能”处理，不承诺 P6/P9 数字；
  UI 可提示“长 GOP，定位可能较慢”，不做近似帧交付。
- P8 不变：长按 ≥12 帧/秒，每帧呈现；P7 的缓存路径同时服务 P8 的首帧/后退。
- 理由：用户目前真实片库样本是短 GOP（1s）；1s 硬解 28ms、2s 76ms、8.3s 230ms。
  方案 A 能保留短/中 GOP 的 80/150/200ms 强承诺；长 GOP 不伪装达标，但仍可用、仍精确。

**代价**：长 GOP 素材在性能上归“可用档”，不是保证档；如果以后大量出现长 GOP，
需要重新评估是否放宽 P6/P9。

### 方案 B：按关键帧距离分档放宽（不设 GOP 门槛）

- P7 仍按方案 A 改为 ±1。
- P6/P9 按目标帧距前关键帧的距离分两档：
  - 短距（≤2s）：1080p P6 ≤150ms / P9 ≤200ms；4K ≤300/300ms。
  - 长距（>2s）：1080p P6 ≤300ms / P9 ≤300ms；4K ≤500/500ms。
- 所有素材仍留在保证档的“帧准确”承诺内，但性能数字整体变弱；
  验收要按距离分类取样，测试矩阵更复杂。
- 理由：如果长 GOP 是主场景，这比“把长 GOP 推去可用档”更诚实；
  但用户当前片库没有长 GOP，收益不足。

### 方案 C：只改缓存/预取

- 只增加帧缓存、前向预取、精确 seek 保留帧。
- 只能让 ±N 步进接近 0ms，**不能**让任意远跳变快；单独用解决不了 P9。
- 结论：不作为独立方案，只能作为方案 A/B 的实现手段。

## 4. 推荐：方案 A 的具体改动

### 4.1 spec §4.1

- P7 改为“±1 帧步进（PgUp/PgDn/方向键）”；明确不含输入帧号/点击远跳。
- P6、P9 增加条件：“目标帧距其前一个关键帧 ≤2s；超过按可用档性能处理。”
- 4K 放宽档补 P9：4K P9 ≤300ms；P6 ≤300ms、P7 ≤150ms 不变。
- 测试方法：
  - P7：解码器已热、目标 ±1，双向；精确 seek 后紧接 PgUp/PgDn 各测一次；
    另测“跨 GOP 边界后退”（目标为关键帧，PgUp 到前一 GOP 末帧），2s GOP 必须 ≤80ms，
    超则把 P7 边界条件收紧到 1s（或接受该边界按 P6/P9 预算）。
  - P6：产品拖动预览 + 松手，不用冷 seek 探针代替。
  - P9：冷随机跳转，20 个目标；记录每个目标的关键帧距离，只有 ≤2s 的样本计入保证档。
  - P8：同方向长按，2s ≥20 帧，每帧呈现。

### 4.2 spec §4.2

- 保证档性能条件加一句：
  “P6/P9 的数字以目标帧距前关键帧 ≤2s 为前提；P7 的 ±1 以热解码器/缓存为前提，
  跨 GOP 边界未命中时按同一 2s 条件处理；长 GOP 仍支持打开、播放、帧精确，
  但性能按可用档处理。”
- 不改变 H.264/H.265/8-bit SDR/分辨率/帧率的支持矩阵；只限定性能承诺。

- `plan.md` §4.3/§5.5/§7 R1：把 P7 的“随机 seek”表述改回 ±1；P6/P9 增加 GOP 条件；
  4K P9 补 300ms。
- `tasks.md`：
  - T2.3：精确 seek 按目标距关键帧分类记录；
  - T2.4：P7 验收改为 ±1（双向、热解码器、缓存命中），并单列跨 GOP 边界后退；
  - T2.9/T2.10：P6 用产品拖动路径测，不用探针代替；
  - T7.4：4K P9 300ms；
  - T7.7：验收报告记录每个 P6/P9 样本的 GOP 距离，长 GOP 样本单列。
