## 2. 本轮做了什么

### 2.1 有界 LRU 帧缓存

[`src/media/FrameCache.h`](../src/media/FrameCache.h) / `.cpp`：

- `std::list` + `unordered_map` 的 LRU；`SetLimits(max_bytes, max_entries)`、
  `Put/Get/Contains/Clear/stats`。
- **只缓存软件帧**：软件帧 `av_frame_clone` 增加 AVBuffer 引用；D3D11VA 硬件帧在
  `Put` 时用 `av_hwframe_transfer_data` 回拷到 NV12/P010，**不长期持有解码表面**，
  避免把解码器池耗尽。
- 预算按分辨率固定，不随片长增长：
  - 1080p：64MiB / 24 帧（字节先到上限时实际 21 帧，65,318,400B）；
  - 4K：96MiB / 8 帧（8 × 12,441,600 = 99,532,800B）；
  - 720p 及以下：32MiB / 24 帧；10-bit 按 P010 3B/像素。
- `stats()` 暴露 entries/bytes/max_bytes/max_entries/hits/misses/puts/evictions；
  `FrameCache::LimitsForFrame` / `FrameBytesFor` 纯函数，测试可断言。

### 2.2 缓存策略：只服务后退步进

`FrameCacheMode` 只有两个值：

- `kNone`：普通跳转、时间轴/标记跳转、拖动松手、前进步进、播放循环、内部定位；
  不读不写，保证解码器停在目标帧之后。
- `kBackwardWindow`：后退步进（PgUp/←/上一帧按钮/连发）先查缓存；未命中时从
  关键帧解码到目标，并把**目标之前一窗帧**写入缓存；后续连续后退直接命中。

为什么不做 target-only（ADR-005 字面上的“精确 seek 路径解过的帧也保留”）：
实测每次普通跳转多一次 1080p 3.1MB 回拷，`--mark-test` 精确画面 p95 从
31.55ms 抬到 71.12ms；而连续后退的下一个目标是“当前帧−1”，target-only 里没有，
命中率仍为 0。因此按测量收窄为“后退步进预热一窗”，不是放弃帧缓存。

### 2.3 MediaSession / PlaybackController

[`src/media/MediaSession.h`](../src/media/MediaSession.h) / `.cpp`：

- `SeekToFrame(frame, out, error, FrameCacheMode mode = kNone)`；
  缓存命中返回 `last_hit_frame_`（软件帧），生命周期到下一次 `SeekToFrame`/`Close`，
  沿用“解码器帧只在下次 Decode 前有效”的契约。
- 命中后 `decoder_stale_ = true`；`EnsureSequentialPosition(frame, error)` 在起播前
  必要时重新 seek（`kNone`），否则 `PlaybackController::Tick` 会从错误的解码位置续播。
- `Open`：先清缓存/命中帧，成功后按 `probe_.info.video.width/height/bit_depth`
  设置预算；首帧已解码，`decoder_stale_ = false`。
- `Close` / `InstallIndex`：清缓存、释放命中帧、`decoder_stale_ = true`；
  新索引可能改变帧号/PTS 映射，不能留旧缓存。
- `FrameCache` 非线程安全，只在 GUI 线程使用；不跨线程共享。

[`src/app/PlaybackController.cpp`](../src/app/PlaybackController.cpp)：

- `Play()` 在真正进入播放前调用 `session_->EnsureSequentialPosition(current_frame_)`；
  失败则打 `T7.2 play_position_failed` 并退出播放（不静默从错帧起播）。
- `SeekToFrameInternal`（循环回 A/定帧回 A）显式用 `kNone`，必须让解码器停在目标后。

### 2.4 MainWindow

[`src/app/MainWindow.cpp`](../src/app/MainWindow.cpp) / `.h`：

### 2.6 内存测量模式

新增 [`src/app/ProcessMemory.h`](../src/app/ProcessMemory.h) / `.cpp` 与
[`src/app/MemoryTestRunner.h`](../src/app/MemoryTestRunner.h) / `.cpp`：

- `SampleProcessMemory` 用 `GetProcessMemoryInfo`（`PROCESS_MEMORY_COUNTERS_EX`）
  取 `WorkingSetSize` / `PeakWorkingSetSize` / `PrivateUsage`，另取 handle 数。
- `--memory-test` + `--memory-mode empty|pause|play|step|switch`：
  - 产品异步索引路径；等 `IndexReadyForTest()` 后才采样；
  - 全开 10s 超时/打开失败 exit 2；模态框 250ms 自动关闭，避免测量挂死；

  - 每行 `T7.2 memory ... ws_mb/private_mb/peak_ws_mb/handles/playing/cache`；
    最后一行 `T7.2 memory_summary ... limit_mb/pass`；
  - `step` 走真实 PageUp/PageDown（窗口事件过滤器），记录每次耗时 p50/p95/max。

## 4. 决策与口径

1. **P10 用“打开并暂停 60s”**：不把连续步进后的高水位混进 P10；空态另报 63.8MB。
2. **P11 播放期间缓存为空**：帧缓存只在后退步进预热；播放路径不写缓存，所以
   P11 与加缓存前基本一致。
3. **硬件帧回拷到软件再缓存**：避免长期持有 D3D11VA 表面；代价是后退窗口填充时
   每次约 1–3ms/帧。1080p 24 帧窗口的 p95 32.72ms 仍低于 P7 80ms。
4. **只后退步进写缓存，不做 target-only**：见 §2.2 的 71.12ms / 0 命中证据。
5. **缓存命中后起播必须重新定位**：`decoder_stale_` + `EnsureSequentialPosition`；
   不这样做会把“后退一步再播放”变成从旧解码位置续播。
6. **切文件清缓存、上限随分辨率切换**：A↔B 每次 `count=0`；WS 高水位有界但
   不承诺立刻回落到新开基线。
7. **波形 4h 硬上限**：V10 2h 只用 5.76MB；上限避免异常长片无界。
8. **4K P7 不通过**：4K 步进 p95 ~228ms；T7.4 专门处理，不在 T7.2 宣称。
9. **`--memory-test` 只做测量**：不改变产品打开/播放/索引路径；不参与常规回归。

## 5. 缺口 / 不宣称

1. **不是基线机**：6C/12T + RTX 4060 + 32GB，强于 4C/8GB/集显。
2. **不是正式 V1/V4/V10**：1080p 是 152s 代理，4K 是 450 帧代理；
   P10 的 V1 是 3–10 分钟真实片，P11 4K 应使用 V4。
3. **不是冷 OS 缓存**：没有清 Windows 文件缓存/重启；首启可能更高。
4. **4K 播放只持续约 15s**：20s/60s 样本是播完保持末帧，不是持续播放 60s。
5. **4K P7 未通过**：p95 ~228–232ms > 150ms；T7.4。
6. **步进高水位不是 P10/P11 稳态**：1080p 333.7MB、4K 593.7MB；
   不把这两个数字写成 P10/P11 通过或失败。
7. **GPU 显存不计入 working set**：D3D11VA 表面在驱动/显存侧；P11 只报进程内存。
8. **没有 2h soak**：P14 的内存/句柄/线程增长留 T7.3。
9. **没有真实 VFR/HDR/10-bit 4K、200% 真实显示缩放、多显示器、IME/AltGr**；T7.7。
10. 不把本文写成 P10/P11 正式验收、基线机、正式 V1/V4、2h soak 或 P7 4K 通过。
