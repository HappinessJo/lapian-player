# ADR-001 解码与渲染管线

- **状态**：已接受（2026-10-19 按推荐确认；实现中若证据变化，按“重新考虑条件”修订）
- **日期**：2026-10-19
- **决策范围**：首期视频解码、GPU 呈现、截图回读
- **相关**：`plan.md` §2.1、§4；`ADR-004` 依赖与许可

## 背景

首期要求帧精确 seek、VFR 帧号、4K/HEVC 可播、冷启动 ≤1.5s、空闲 ≤250MB、分发 ≤100MB、零网络。播放只是手段，**帧号与定位才是产品语义**，因此管线必须能拿到每一帧的 PTS、关键帧信息，并能按“帧序号 → 时间戳”精确解码到目标帧。普通播放器的“跳到最近关键帧”不够。

## 决策

1. 用 **FFmpeg**（avformat/avcodec/swscale/swresample，LGPL、动态链接、最小构建）负责解封装与解码；H.264/H.265 优先走 **D3D11VA 硬件解码**，失败回退软件解码。
2. 用 **D3D11 flip-model swapchain** 直接呈现 NV12/P010 纹理，片元着色器做 NV12/P010 → sRGB（BT.709 limited range）转换与窗口适配缩放；不使用 Qt 绘制视频帧。
3. UI 用 **Qt 6 Widgets**，视频区域是一个原生子窗口/交换链表面；时间轴、侧栏、输入框由 Qt 绘制。
4. 截图通过 `av_hwframe_transfer_data`/GPU 回读拿到源分辨率帧，**按容器 display matrix 旋转到显示方向**，用 **WIC** 编码 PNG；不复用屏幕截图。
5. 色彩只做 8-bit SDR 的基础转换；10-bit/HDR 可解但提示“颜色不保证”，不做 tone mapping/色彩管理。
6. 旋转在渲染阶段按容器 display matrix 应用；截图输出与显示方向一致；首期不做手动旋转。

## 备选方案

| 方案 | 结论 | 原因 |
|---|---|---|
| Media Foundation 单栈 | 否 | HEVC 依赖系统扩展；VFR/帧索引/精确 PTS 控制弱；行为随系统版本变化 |
| libmpv 作为播放引擎 | 否 | 帧号/VFR/逐帧语义难精确控制；包体与行为定制成本高；与“帧是第一等公民”冲突 |
| Qt Multimedia / QVideoSink | 否 | 时钟、缓冲、seek 精度不可控；4K 性能与零拷贝不保证 |
| Electron + WebCodecs | 否 | P1/P10/P12 基本不可能；VFR/索引控制弱 |
| 纯软件解码 + GDI/D2D | 否 | 4K 播放与拖动性能不达标；CPU 占用高 |

## 为什么这样选

- **帧精确**：FFmpeg 给出每帧 PTS/关键帧，配合自建索引与“关键帧回退 + 解码到目标 PTS”，才能保证落点误差 0 帧。
- **性能**：D3D11VA 硬解 + GPU 缩放，4K 解码/呈现成本可控；软件回退保证兼容。
- **体积/启动**：Qt Widgets + 最小 FFmpeg 比 Electron/Qt Quick 更小、更快；动态链接满足 LGPL。
- **可控性**：渲染与解码分离，预览/精确两条路径可独立调度；截图能拿源分辨率帧。

## 后果

- 正面：帧语义、VFR、截图、性能都可控；依赖边界清晰；竖屏素材方向与截图一致。
- 负面：需要自己维护 D3D11 设备丢失、色彩转换、硬件帧回读与旋转；FFmpeg 最小构建需要维护构建脚本与许可文件。
- 风险：不同 Intel/AMD/NVIDIA 驱动的硬解行为差异；RDP/虚拟机可能无硬解；旋转叠加缩放时坐标/命中需要单独测试。

## 重新考虑的条件

- FFmpeg 最小构建仍使 P12 超 100MB，或 Qt LGPL 合规成本不可接受。
- Media Foundation 在某代 Windows 上对 HEVC/VFR 的精确性明显更好，且能保持 P1/P10。
- 首期之后要做 HDR/10-bit 色彩管理（需要换渲染/色彩管线，另立 ADR）。
- 要做多视频轨/多窗口，现有单表面假设不再成立。
- 需要手动旋转、非方形像素、或“截图保存源像素而非显示方向”的需求。
