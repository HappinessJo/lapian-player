## 背景

v1 的引擎假设"一个本地文件、可随机读、有完整 moov"。在线模式打破三个前提：

1. 数据来自网络，**未缓存区域不存在**，"读到 EOF"不等于"文件结束"；
2. B 站主路径是 **DASH 音视频分离**，v1 的"一个容器两条流"不成立；
3. 清晰度与编码**逐片不同、逐账号不同**（见 spike §2）。

spike 实测（2026-10-22）给出三条硬事实：

- `durl` 单文件路线在 2/3 样本上给 720p，且 **moov 在文件头**：512KB 即可解首帧并报出完整时长/帧率 → 帧号精确、无需"扫描中"。
- `dash` 路线匿名恒 480p30，但结构清晰：`init 0-916`、`sidx 917-1244`，Range 206 可用。
- 起播瓶颈在解析与握手（view 60–142ms + playurl 71–88ms），不在缓冲；**全量下载才是瓶颈**（最坏 1.27MB/s，3 分钟 1080p 约 47s）。
- 登录（普通用户，非大会员）后 **DASH 稳定给 1080P30（3/3）**，但 **`durl` 的 1080p 只有 1/3 样本**；**1080P60 与 4K 均不可得**（见 spike §2.2）。

因此"先下完再播"不能作为主路径；"边看边缓存"必须落到**可增长文件**上。

## 决策

### D1 解析与取流分层
解析层只做"BV/URL → 元数据 + 候选流列表（含档位/编码/帧率/大小/过期时间）"，不碰播放。播放层只接收"本地可读路径"。两层通过一个显式数据结构交接，便于解析规则独立更新、失败时给可读原因。

### D2 缓存形态：标准 mp4 文件，成品可脱离在线模式
- 缓存落 `<缓存根>/<bvid>/<qn>-<codecid>/`，下载中为 `.part`，完成或达到可播阈值后原子改名为 `.mp4`。
- 配额 20GB，LRU 淘汰；占用可见、可手动清空。
- **命中缓存时零网络打开**，与本地模式走同一条代码路径（v1 能力全量可用）。
- 不做"缓存导出/分享"入口。

### D3 播放读层：可增长文件
`MediaSession` 的读层改为"已缓存区间可读；读到未缓存字节时阻塞并上抛缓冲状态"，而不是把当前末尾当 EOF。UI 据此显示"缓冲中"，取到后继续。这条对 durl 单文件和 DASH 双流都成立，是**两项共用的唯一新基础设施**。

**已由 spike 验证**（[报告 §4.1](../perf/v2-online-spike.md)）：自定义 AVIO 阻塞读成立，0.3MB 已缓存即可出首帧（5.2ms）；未缓存区 seek 等待 ≈（剩余字节 ÷ 速率），落点误差 0（100+ 次 seek）；已缓存区 seek 零阻塞；**取消可在 3–15ms 内打断阻塞读**（`AVERROR_EXIT`）。**未验证**：并发读。

### D4 单文件优先，DASH 用双输入
- **默认路径**：能拿到可接受档位的 `durl` 单文件时，直接顺序缓存 + 可增长文件播放。零 remux、帧表完整。
- **DASH 路径**：不 remux，采用**双输入**——视频与音频各自一个 `AVFormatContext`，共用时钟与 seek 协调。理由：复用 v1 的精确 seek/索引/波形路径，避免 muxer、二次写盘与"全量下载才可播"。
- **明确不选**"先下完再 remux"作为主路径（慢网络起播不可接受）；仅在 D4 未完成前作为临时降级。
- **登录档数据修正**：`durl` 1080p 只有 1/3 命中（S-2 可得，S-1/S-3 仍卡 720p）→ 单文件路线只能保证 720p；**1080p 必须走 DASH 双流**。

### D5 运行时不得调用 GPL 的 ffmpeg.exe
spike 里用的 `third_party/tools/ffmpeg-gpl` 只是测量工具。产品运行期继续只用 LGPL 动态链接的 libav*（ADR-004），不引入子进程 remux。

## 备选方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 单文件 durl 渐进（D4 默认路径） | **是** | 实测可行；引擎改动最小；帧表完整、无需扫描态 |
| DASH 双输入渐进（D4 第二路径） | **是，但工作量大** | 唯一能覆盖 1080p/60fps/4K 的路径；需要改`MediaSession`/`AudioDecoder`/`FrameIndex`/波形 |
| DASH 全量下载 + remux | 降级 | v1 零改动，但慢网络下 1080p 起播 10–60s，违背"几秒起播" |
| 本地 HTTP 代理 + 虚拟 mp4 | 否 | 多一个进程/端口/生命周期，收益不抵复杂度 |
| FFmpeg 直接开远程 URL / 自写 MPD | 否（主路径） | 无本地缓存语义，seek 行为依赖网络；只作对照实验 |
| 全量下载后再播 | 否（主路径） | 起播时间不可控 |

## 为什么这样选

- **先保住"帧号精确"这个差异化**：durl 单文件的 moov 在头部，帧表与总帧数**从第一秒就精确**，不需要 v1 已有的"扫描中"降级；DASH 双流则必须接受"总帧数随缓存增长"。
- **把新基础设施压到最小**：两条路径共用"可增长文件读层"，这是唯一无法回避的改造。
- **不让清晰度上限被架构锁死**：单文件优先不等于只做单文件；DASH 双输入是清晰度上限的必要投入。
- **合规**：运行期只用 LGPL 库，不用 GPL 工具链；不做绕过，只取凭据内允许的流。

## 后果

- 正面：默认路径上线快、体验接近本地；缓存成品可被 v1 本地模式直接打开；本地模式零网络不受影响。
- 负面：在线模式必须区分"已缓存/缓冲中"，**P7 ≤80ms 只在已缓存区间承诺**；DASH 路径的总帧数、波形会出现"生成中"状态。
- 风险：可增长读层的阻塞语义若设计不当，会出现死锁、seek 卡住、UI 假死；**阻塞中的读必须可取消**（用户 seek/关窗时立即打断），否则关闭窗口或快速连拖会挂住；URL 120 分钟过期需要刷新与重试；缓存损坏需要可重建；**HTTP 层必须用产品实际栈做"带 SESSDATA 的 nav 自检"**（同一 Cookie：curl 通过、.NET HttpClient 返回 -101，见 spike §3.5）。
- 已决："durl 能不能直接给 1080p 从而省掉 DASH"——**答案是不能**（1/3 命中）。DASH 双输入是 1080p 的必要路径。

## 重新考虑的条件

- `durl` 的 1080p 命中率在更大样本上显著提高（例如 >90%）→ 可把单文件路线提升为 1080p 主路径，D4 第二路径降级。
- 大会员档实测显示 1080P60 / 4K 可达 → 需要为这些档补性能与色彩口径（v1 的 4K 只是可用档），并重新评估 D4 的成本。
- 可增长读层在 spike 复现中出现不可解的阻塞/死锁 → 退回"全量下载 + remux"并重新评估"几秒起播"的承诺。
- B 站改成强制分片/DRM → 在线模式整体重新评估。
- 若允许使用 GPL 组件（需重新评审 ADR-004 与分发许可）→ 可考虑子进程 remux，但这会改掉本 ADR 的 D5。
