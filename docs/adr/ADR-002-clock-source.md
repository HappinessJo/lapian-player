# ADR-002 主时钟与音画同步

- **状态**：已接受（2026-10-19 按推荐确认；实现中若证据变化，按“重新考虑条件”修订）
- **日期**：2026-10-19
- **决策范围**：播放、循环、变速时的媒体时钟；步进/拖动的音频状态
- **相关**：`plan.md` §3.5、§6；`ADR-001`

## 背景

首期同时要求：正常播放有声、2x 变速音画偏差 ≤1 帧、A/B 循环不黑屏、逐帧步进/拖动静音、2 小时播放内存稳定。音频设备时钟与系统时钟会缓慢漂移；如果视频用自己的定时器、音频自由播放，长播后必然不同步。必须选一个主时钟，并明确步进/拖动时音频停在哪里。

## 决策

1. **有音频且可播放时，音频设备时钟为主时钟**：用 WASAPI `IAudioClock` 的已播放帧数换算媒体时间；视频按该时间选择/呈现帧。
2. **无音频、音频解码失败、设备丢失时，系统单调时钟（QPC）为主**；接口不变。
3. 暂停、步进、拖动、点击时间轴：**时钟暂停 + 音频静音**；恢复播放时把音频 seek 到当前帧 PTS，再启动时钟。
4. 变速通过改变重采样比与时钟速率实现；音频主时钟继续生效，视频允许掉帧追赶。
5. 循环/seek：flush 音频缓冲，重置 `anchor_pts`；视频保持上一帧直到目标帧就绪。
6. 全局 A/V 偏移只估一次（首包 PTS + priming/edit list），同时用于波形与音频起播；运行中不动态补偿。

## 备选方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 视频主时钟 + 音频重采样伺服 | 否 | 音频设备时钟与 QPC 漂移会让 2h 播放逐渐偏；伺服实现复杂、易 underrun |
| 始终用系统时钟 | 否 | 音频按设备时钟播放，长播必漂移；2x 更明显 |
| 1x 音频主、变速视频主 | 否 | 两套时钟切换点多，循环/变速边界易出 bug；收益不足 |
| 音频主时钟（本决策） | 是 | 音频连续、视频向音频对齐；步进/拖动本来就要静音，切换成本低 |

## 为什么这样选

- **≤1 帧同步**：视频帧选择直接由音频已播放样本数驱动，不需要估计“音频跑到哪了”。
- **2 小时稳定**：音频设备时钟是播放的真实时间基准，不会累积 QPC 与声卡之间的漂移。
- **步进/拖动简单**：这两类操作 spec 本来就要求暂停 + 静音，时钟暂停即可；恢复时一次 seek 对齐。
- **变速自然**：重采样比变化直接改变“每秒消费多少源样本”，时钟速率同步变化。

## 后果

- 正面：同步逻辑单一；2x 掉帧时音频不断、帧号真实；步进/拖动不产生爆音。
- 负面：音频设备异常时必须降级；视频解码跟不上时只能丢帧（2x 允许，1x 保证档需硬解达标）。
- 风险：`IAudioClock` 在部分驱动上精度/行为差异；设备切换（默认输出变化）需要重建并重锚。

## 重新考虑的条件

- 保证档 1x 播放出现持续丢帧，说明音频主时钟 + 解码能力不匹配。
- 需要“拖动音频擦洗”或“变速保持音高”（候选池）——会引入独立音频时钟/时间拉伸，需重写本 ADR。
- 需要多音轨切换或外部音频输出设备选择。
- 实测 2h 音频设备时钟漂移不可接受（概率低）。
