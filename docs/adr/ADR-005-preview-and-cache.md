# ADR-005 拖动预览与帧缓存策略

- **状态**：已接受（2026-10-19 按推荐确认；实现中若证据变化，按“重新考虑条件”修订）
- **日期**：2026-10-19
- **决策范围**：拖动预览、松手精确、步进缓存、预取
- **相关**：`plan.md` §3.2、§3.3、§4.2、§4.3

## 背景

spec 要求拖动中“降质实时预览、≥30fps、无 >200ms 停顿”，松手 ≤150ms 精确到帧；同时步进 p95 ≤80ms、长按 ≥12 帧/秒且每帧呈现。4K 长 GOP 下，“每个拖动事件都从关键帧精确解码到目标”在预算内不可能；但“只显示关键帧”又会让预览几乎不动。必须在预览质量、响应性、精确性之间做一个明确取舍。

## 决策

1. **两条解码路径**：
   - **PreviewDecoder**：只服务拖动；seek 到目标之前最近的关键帧，在每次约 15ms 预算内向前解码；发布“目前最新的帧”；请求覆盖式（队列深度 1），过期结果按 generation 丢弃。
   - **ExactDecoder**：服务松手、步进、帧号输入、标记跳转；从关键帧解码到目标 PTS，落点误差 0；优先于预览。
2. **UI 呈现策略**：拖动中每 vsync 呈现“最新可用帧”，允许落后于指针、允许降采样/跳帧；**绝不清空画面**；帧号显示目标帧，松手后校正为实际呈现帧。
3. **松手切换**：取消预览、清空预览队列、ExactDecoder 独占；若目标在当前 GOP 内则继续向前解，否则关键帧回退。
4. **帧缓存**：LRU，按分辨率设上限（1080p 约 16–24 帧，4K 约 6–8 帧）；缓存当前 GOP 附近；后退步进优先命中缓存；前向预取 N+1…N+4。
5. **不做**：不做代理转码、不做全片缩略图图集、不做后台预生成预览缓存、不做“拖动时音频擦洗”。

## 备选方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 拖动也走精确解码 | 否 | 长 GOP/4K 下每事件几十到几百 ms，P4/P5 必失败 |
| 只显示最近关键帧 | 否 | 响应快但画面按 GOP 跳变，不满足“实时预览”的产品意图 |
| 预生成代理/缩略图 | 否 | 违反冷启动、体积、磁盘预期；首期不做预处理 |
| 拖动时降低解码分辨率（decoder lowres） | 部分可用 | 仅部分 H.264 支持；HEVC/4K 不可依赖；作为预览辅助而非主策略 |
| 双解码路径 + 最新帧 + 缓存（本决策） | 是 | 响应性与精确性分离；不引入预处理；内存可控 |

## 为什么这样选

- **P3/P4/P5**：拖动主路径不做同步精确 seek；UI 每 vsync 都有东西可呈现，不会被单个长 GOP 卡住。
- **P6/P7**：松手/步进走精确路径；帧缓存让后退与连续步进在预算内。
- **帧准确**：预览允许近似，但**交付帧**（松手、步进、输入、标记跳转）必须是精确帧；预览帧永远不会被当成目标帧记录。
- **内存**：缓存上限按分辨率固定，不随片长增长；2h 播放不会因缓存膨胀。

## 后果

- 正面：拖动跟手、松手精确、步进快；实现边界清楚，可单测/可压测。
- 负面：拖动中画面可能明显落后于指针（快速拖过长 GOP 时）；需要 generation/取消逻辑，否则易出现“旧帧覆盖新帧”。
- 风险：4K 预览可能低于 20fps（spec 放宽档）；长 GOP 精确 seek 仍可能超 P6/P7（见 plan R1），本 ADR 不能消除物理成本。

## 重新考虑的条件

- V1–V4 实测拖动预览明显不可用，或用户接受“首次打开后台生成代理缓存”（会改 P1/P2/P12，需 spec 变更）。
- P6/P7 在真实片单上稳定超标，需要把“限制保证档 GOP”或“放宽指标”写成规格。
- 首期之后要做音频擦洗/时间轴缩略图预览（候选池），需要另一套缓存与时钟策略。
