## 3. S2 硬事实（已实测，不要再论证）

- **匿名**：DASH 恒 480p30；`durl` 720p 只在 2/3 样本出现，60fps 样本只给 360p。
- **普通用户登录（非大会员）**：DASH 稳定 **1080P30（3/3）**；`durl` 的 1080p **只有 1/3 命中**；**1080P60 与 4K 均不可得**。
- 1080p AVC 码率 **2.1–2.6 Mbps**（3 分钟约 47–59MB；20GB ≈ 5.6–6.8 小时）；HEVC/AV1 约为 AVC 的 1/3。
- 起播阈值 **≈0.16–0.3MB**（`open`/`find_stream_info` 也要等数据）；TTFB 33–75ms；吞吐 0.95–10.24MB/s（方差大）。
- playurl URL 有效期 **120 分钟**；每流 3 个备份 URL。
- **可增长读层已验证**：0.3MB 即出首帧（5.2ms）；未缓存 seek 等待 ≈（剩余字节 ÷ 速率），落点误差 0；**取消 3–15ms 打断**。
- **同一 Cookie：`curl.exe` 通过（code=0/isLogin=true），.NET `HttpClient`/`Invoke-WebRequest` 一律 -101**（无代理，UA/HTTP 版本无关）→ 产品 HTTP 栈必须自检。
- 失败码：`-400` 格式错误、`-404 啥都木有`、`62002 稿件不可见`；**BV 校验位有效可能命中另一条视频** → 必须回显标题/时长让人确认。
- 60fps 源降 30fps：实测 2867×2 = 5734，**精确 2:1**（只验了一条）。

## 4. 未验证（S3 不许当成已验证）

1. **大会员档**：1080P60 / 4K 能否达到、编码是否只有 HEVC/AV1。
2. **并发读**：seek 引擎 / 预览解码 / 波形线程同时取数。
3. **网络异常**：断网、URL 过期、缓存文件被占用/损坏。
4. 其他 60fps 素材是否同样精确 2:1。
5. 真实网络抖动下的起播与缓冲体验。

## 5. S3 需要用户拍板的点（不要自己定）

1. **交付顺序**：M1（`durl` 720p 单文件闭环，工程量最小）先做，还是直接 M2（DASH 双输入 1080p）。
2. **在线验收数字**：起播 p95 ≤5s 是否接受；已缓存 P7 沿用 80ms；任务完成率目标（草案 80%）。
3. **登录自检**：放启动自检，还是只在"打开 BV 时"诊断。
4. **60fps 提示形态**：进片横幅 / 帧号旁角标 / 详情页。
5. **缓存配额验收**：20GB + LRU 如何验（手工清空、模拟磁盘满）。

## 6. 复现命令

```powershell
# 档位矩阵（匿名）
pwsh -NoProfile -ExecutionPolicy Bypass -File docs\perf\spike\probe6.ps1

# 登录档（需要 .secrets\bilibili_sessdata.txt 或 bili_sessdata.txt）
pwsh -NoProfile -ExecutionPolicy Bypass -File docs\perf\spike\probe_login_curl.ps1

# 可增长读层探针
cmake -S docs\perf\spike\growing -B %TEMP%\growing-build -G "Visual Studio 17 2022" -A x64 `
  -DFFMPEG_ROOT=<repo>\third_party\ffmpeg\build-msvc\ffmpeg-7.1.1-minimal
cmake --build %TEMP%\growing-build --config Release
# 把 FFmpeg bin 加进 PATH，然后：
growing_probe.exe <file.mp4> <初始缓存MB> <速率MB/s> [baseline|cancel <ms>]
```
