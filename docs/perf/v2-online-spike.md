# v2 在线可行性 spike（S2 测量报告）

- **版本**：v0.2（2026-10-22 深夜，补普通用户登录档、可增长读层、取消验证）
- **状态**：**匿名档 + 普通用户登录档完成**；大会员档、并发读、网络异常（断网/URL 过期/缓存损坏）未验。结论为"有条件 GO"，见 §0.1。
- **目的**：回答"边看边缓存"能不能做到可用，为 S3 规格与 `ADR-007` 草案提供数据。
- **边界**：不写产品 UI、不改 `spec.md`、不动 v1 阈值/基线；只做只读解析与取流观测，不批量抓取、不再分发。

---

## 0. 结论摘要

**有条件 GO。** 三条公开片都跑通了"解析 → 取流 → 本地缓存 → ffmpeg 播放 → 已缓存区 seek"，技术上没有阻断项。但**真正的问题不在技术，在档位**：

1. **匿名 DASH 恒定 480p30**（三条片全部只回 `vid=16/32`），而 API 的 `accept_quality` 照样列出 1080P/1080P+。
2. **`quality` 字段会撒谎**：请求 `qn=116`，返回 `quality=64`，但 dash 里根本没有 64 档。判断档位只能看 `dash.video[]` 实际列表。
3. **60fps 源匿名连帧率都丢**：`BV1mA411m7pS`（标题 UHD 60FPS）匿名只给 `852x480@29.412fps`。→ 帧号与源片错位，Q3 的"保帧率优先"在匿名档**无从实施**。
4. **`durl` 单文件路线比 DASH 简单一个量级**，但清晰度**逐片不同**：2/3 样本给 720p 单文件，60fps 样本只给 360p。
5. **durl 单文件把完整 sample table 放在文件头**：只下 512KB，ffmpeg 就能报出完整时长 110.53s、分辨率、帧率。→ 帧号/总帧数/波形时间轴**从第 0 秒起就是精确的**，不需要"扫描中"。
6. **可增长读层已被探针验证**（§4.1）：自定义 AVIO 阻塞读成立，0.3MB 已缓存即可出首帧；seek 超出缓存时按"剩余字节 ÷ 速率"等待，落点误差 0。→ ADR-007 的 D3 不再是假设。

7. **登录（普通用户、非大会员）只在 DASH 上解锁 1080P**：3/3 样本出现 `vid=80`；`durl` 的 1080p 只有 1/3 样本可得（S-2，25.45MB），另两条仍卡 720p。**1080P60（116）与 4K（120）对普通用户不可得**。
8. **同一个 SESSDATA，curl 能登录、.NET 的 HttpClient/WebRequest 一律返回 `-101`**（无代理；换成 HTTP/1.1、改 UA 都不影响）。这是客户端指纹/传输层差异，**产品选 HTTP 客户端时必须实测**。

**因此**：`ADR-007` 的核心分歧不是"缓存怎么实现"，而是**"要不要为了 1080p 必须处理 DASH 音视频分离"**。登录档数据给出的答案是：**要**——`durl` 拿 1080p 只有 1/3 命中率，不能作为保证。

### 0.1 go/no-go（S2 结论）

**GO（有条件）。** 三条公开片跑通"解析 → 取流 → 本地缓存 → 播放 → 已缓存区 seek"，可增长读层与取消已由探针验证。**进 S3 不需要等大会员档。**

条件与收窄：

1. **交付分两步**：M1 用 `durl` 单文件做 720p 渐进闭环（工程量最小、最快验证产品假设）；M2 做 DASH 双输入补 1080p。**先做 M1 ≠ 砍掉 1080p**——决定 3/4 的承诺要由 M2 兑现。
2. **60fps 帧号不可对齐**是硬限制（普通用户没有 60fps 档）。已写进 vision 决定 3 与风险表：强提示 + 标记/截图记录 fps，不假装对齐。
3. **4K / 1080P60 未验证**：只存在于大会员侧。S3 不得把它们写成 MVP 验收项，只能写"若可达则按可用档处理"。
4. **HTTP 栈必须自检**：产品实际客户端要能通过"带 SESSDATA 的 nav"，否则登录形同虚设（§3.5）。
5. **P7 ≤80ms 只承诺已缓存区**；未缓存区显示可估算的缓冲进度，不承诺数字。

**可带进 S3 的未验证项**：并发读、断网/URL 过期/缓存损坏、大会员档。

## 2. 档位矩阵

### 2.1 匿名

| 样本 | `accept_quality`（声称） | `durl` qn=64 实际 | `durl` qn=80 实际 | `dash` 实际 vid | 实际帧率 |
|---|---|---|---|---|---|
| S-1 | 112,80,64,32,16 | **64（720p）** 13.67MB | 64 | 16,32 | 30 |
| S-2 | 116,80,64,32,16 | **16（360p）** 3.93MB | 16 | 16,32 | 29.412 |
| S-3 | 112,80,64,32,16 | **64（720p）** 49.57MB | 64 | 16,32 | 25 |

### 2.2 登录（普通用户，非大会员，Lv6）

| 样本 | `durl` qn=120 实际 | `dash` 上限 | 1080p AVC 码率 | 1080P60 / 4K |
|---|---|---|---|---|
| S-1 | 64（720p）13.67MB | **80（1920x1080@30）** | 2249k | 不可得 / 不可得 |
| S-2 | **80（1080p）25.45MB** | **80（1920x1080@29.412）** | 2125k | 不可得 / 不可得 |
| S-3 | 64（720p）49.57MB | **80（1920x1080@25）** | 2629k | 不可得 / 不可得 |

- `format` 字段：720p 单文件为 `mp4720`，360p 与 1080p 单文件为 `mp4`；`durl_count=1`。
- 480p 档同时提供 AVC(`codecid=7`) / HEVC(`12`) / AV1(`13`)；1080p 档 HEVC/AV1 码率约为 AVC 的 **1/3**（741–830k vs 2125–2629k）。
- **结论 1**：匿名"最高画质" = `max(durl, dash)`，durl 不可预期、dash 恒 480p。
- **结论 2**：登录后 DASH 稳定给 1080P30，但 **durl 的 1080p 只有 1/3 样本**——单文件路线不能作为 1080p 保证。
- **结论 3**：普通用户拿不到 1080P60，也拿不到 4K；**60fps 素材只能拿 30fps 副本**（S-2 的 1080p 是 29.412fps）。
- **结论 4（容量）**：1080p AVC 2.1–2.6 Mbps → 3 分钟约 **47–59MB**；20GB 配额 ≈ **5.6–6.8 小时** 1080p。

## 3. 取流与 HTTP 行为

### 3.1 Range 与首字节

| 观测 | 值 |
|---|---|
| `Range: bytes=0-524287`（durl 720p） | `206`，`Content-Range: bytes 0-524287/14330392` |
| `Range: bytes=0-1048575`（durl 360p） | `206`，`Content-Range: bytes 0-1048575/5491505` |
| TTFB（durl 720p，Range 512KB） | 75ms |
| TTFB（dash 480p，整流 GET） | 33ms |
| 3 个备份 URL / 每流 | 是（`backup_url` 2 + 主 1） |

Range 真支持 206，不是"返回 200 全量"。**这是单文件随机 seek 的前提。**

### 3.2 吞吐（方差很大，必须按最坏情况设计）

| 路径 | 字节 | 耗时 | 速率 |
|---|---|---|---|
| dash 480p 视频整流 | 6,635,980 | 618ms | **10.24MB/s** |
| durl 720p 整流 | 14,330,392 | 10,750ms | **1.27MB/s** |
| durl 360p 1MB Range | 1,048,576 | 1,057ms | 0.95MB/s |
| dash 音频整流（94kbps） | 1,294,290 | 133ms | 9.73MB/s |

同一台机器、同一时段，速率相差 8 倍。**"几秒起播"不能按最好情况算。**

### 3.3 URL 有效期

- `deadline=1792689600` → 本地时间 **2026-10-23 01:24:53**，距观测时刻约 **120 分钟**。
- 含义：单次播放/缓存会话超过 2h 必须刷新 playurl；断线重连也要刷新。

### 3.4 DASH 结构（用于判断"能否只靠 Range 取任意帧"）

| 项 | 值 |
|---|---|
| 视频 `init_range` | `0-916`（917B） |
| 视频 `index_range`（sidx） | `917-1244`（328B） |
| 音频 `init_range` | `0-836` |
| 单流形态 | 一个 URL = init + sidx + moof/mdat 分片，全量 GET 即完整 fMP4 |

### 3.5 客户端差异（重要）

同一个 SESSDATA，用不同 HTTP 客户端请求 `x/web-interface/nav`：

| 客户端 | 结果 |
|---|---|
| `curl.exe`（系统自带，HTTP/1.1） | **`code=0, isLogin=true`**（mid 496594177，Lv6，`vipStatus=0`） |
| PowerShell `Invoke-WebRequest` | `code=-101 账号未登录` |
| .NET `HttpClient`（手动加 Cookie 头） | `code=-101 账号未登录` |

已排除：代理（WinHTTP 直连、无环境变量）、HTTP 版本（curl 强制 HTTP/1.1 仍成功）、UA（改 UA 不影响）、Cookie 编码（原值 / URL 解码值都试过）。

**机制尚未定位**（客户端指纹，或 .NET 对该 Cookie 头的处理），但对产品结论成立：**产品运行期的 HTTP 层必须用实际栈做一次"带 SESSDATA 的 nav 自检"**，失败要映射成可读提示，而不是静默降级成匿名。S2 的登录测量因此改走 `curl.exe`（`probe_login_curl.ps1`）。

## 4. 播放可行性

| 观测 | 结果 |
|---|---|
| dash 480p 只下 **64KB** 能否解首帧 | **能**（exit 0，≈1.1s 视频内容） |
| durl 720p 只下 **512KB** 能否解首帧 | **能**（exit 0，且报出完整 `Duration 00:01:50.53`、1280x720@30） |
| DASH 视频+音频 remux 成单 mp4（faststart） | **54–60ms**，输出 7.63MB / 110.53s，H.264 852x480@30 + AAC 48kHz 立体声 |
| 本地 remux 后打开到首帧 | 52–66ms（含 ffmpeg 进程启动开销） |
| 本地 remux 后 seek 到 50s | 52ms |

**推论**：
- 起播瓶颈是 **API 解析（view 60–142ms + playurl 71–88ms）+ 连接握手**，不是缓冲；首帧所需数据量小到可以忽略。
- 真正的瓶颈是**全量下载**：按最坏 1.27MB/s，3 分钟 1080p（约 60MB）需 **47s** ——"下完再播"路线在慢网络下直接不成立。
- durl 单文件的 moov 在头部 → 帧表完整可得，**不需要在线"扫描中"三态**。

### 4.1 可增长读层验证（自定义 AVIO + 阻塞读）

**目的**：验证 ADR-007 的 D3——"读到未缓存字节时阻塞等待，而不是当 EOF 放弃"。
**探针**：`docs/perf/spike/growing/`（C++，链接**产品同一套 FFmpeg 7.1.1** 导入库，独立构建，不进产品）。
**方法**：后台线程按固定速率推进"已缓存字节"计数；读回调在字节未到时阻塞在条件变量上；同一文件做"完整文件基线"与"边下边读"对照。

| 场景 | 首帧 | seek 到 47.3s（未缓存） | 落点误差 |
|---|---|---|---|
| durl 720p 完整文件（基线） | 5.6ms | 127.1ms | 0 |
| durl 720p 0.3MB @0.5MB/s | 5.2ms | **17854ms（阻塞等待）** | 0 |
| durl 720p 1MB @2MB/s | 5.2ms | **3953ms（阻塞等待）** | 0 |
| dash fMP4 完整文件（基线） | 2.7ms | 57.5ms | 0 |
| dash fMP4 0.5MB @1MB/s | 2.3ms | **3588ms（阻塞等待）** | 0 |

- **阻塞读成立**：0.3MB 已缓存就能出首帧；seek 超出缓存时按"剩余字节 ÷ 速率"等待，取到后落点精确（100+ 次 seek，max err = 0）。
- **未缓存区等待可估算**：实测 ≈（目标偏移 − 已缓存）÷ 速率，UI 可据此显示进度，而不是假装卡死。
- **已缓存区 seek 零阻塞**：回到已缓存区间时阻塞事件数为 0，耗时 7–95ms。
- 每 64KB 触发一次阻塞，事件数与数据量成正比（79–303 次/组），粒度可控。
- **取消可打断**：在阻塞中的 seek 上分别于 500ms / 2000ms 触发取消，实际返回 502.9ms / 2015.3ms（**延迟 3–15ms**）；`av_read_frame` 以 `AVERROR_EXIT` 干净退出，无死锁。→ 产品里"用户拖走/关窗"可以立刻打断等待。
- **`open` 自己也会等**：0.1MB 已缓存 + 0.2MB/s 时 `avformat_open_input + find_stream_info` 花了 305ms；0.3MB 起则 5ms。→ **起播阈值 ≈ 0.16–0.3MB**（moov + stream probe），比"首帧所需字节"更高，慢网下起播时间由它决定。

**一个差点写错的结论**：初版测试目标全落在 5s GOP 网格上（50/10/80…），得出"fMP4 比 durl 慢约 10 倍"；换成不对齐目标（47.3/12.7/83.1…）后两者回到同一量级（16–127ms）。**差异来自测试设计，不是容器**。探针的绝对数字不可用于产品性能承诺（它是单线程 `av_seek_frame` + 解码到目标，不是 v1 的索引/seek 引擎）。

**未覆盖（产品必须补）**：
- **并发读**：v1 的 seek 引擎、预览解码器、波形线程可能同时要数据；探针是单读者。
- 真实网络抖动、URL 过期、连接中断。

## 6. 对架构的约束（实测判定）

| 路线 | 实测可行性 | 代价 |
|---|---|---|
| **A 单文件渐进缓存（durl）** | **成立**：Range 206、moov 在头、512KB 可播、帧表完整 | 档位不可预期；60fps 源可能只有 360p；1080p 是否可得未知（依赖登录） |
| **B DASH 分片/Range 缓存** | **成立**：init/sidx 明确、Range 可取、整流 GET 顺利 | 音视频分离：要么引擎双输入，要么 remux（480p 7.6MB 需 54–60ms，60MB 量级约 0.4–0.5s）；帧索引只能随缓存增长 |
| **C 直连远程 URL** | 能播但不可控：EOF/seek 行为依赖网络，无本地缓存语义 | 不满足决定 1（缓存可见可清），只作对照 |
| D 先下完再播 | 成立但慢 | 慢网络下 3 分钟 1080p 起播 47s，违背"几秒起播" |

**关键结论**：MVP 的技术分叉点只有一个——**是否需要 DASH 双流处理**。若登录后 `durl` 能给到 1080p，单文件路线即可满足全部 MVP 范围，工程复杂度大幅下降；若不能，则必须做双流。

## 7. 待测 / 未覆盖

1. **大会员档**（1080P60 / 4K）：是否可达到、实际编码是否只有 HEVC/AV1、码率与下载耗时。普通用户档已测（§2.2）。
2. **其他 60fps 素材**是否也精确 2:1 降帧（S-2 是 2867×2=5734）；不同片源的转码策略可能不同。
3. **并发读**（§4.1）：多线程同时取数据时的行为（单读者与取消已验）。
4. 断网、URL 过期、缓存文件被占用/损坏时的行为。
5. 无音轨视频的 durl/dash 表现（对应 v1 的 V7 场景）。
6. **HTTP 栈自检**：产品实际使用的 libcurl / WinHTTP 能否通过带 SESSDATA 的 nav 校验（§3.5）。

## 9. 限制

- 单机、单网络、单时段、3 条样本；CDN 速率方差大（0.95–10.24MB/s），本报告不把它当基准。
- 未做合规评审；`62002`/地区限制内容的实际行为只记录不绕过。
- 登录档只覆盖**一个普通用户账号（非大会员，Lv6）**；大会员档与不同账号的风控差异未验。
- 所有数字只代表 **2026-10-22 23:2x – 2026-10-23 00:3x** 这一次观测；B 站接口与档位策略随时可能变。
