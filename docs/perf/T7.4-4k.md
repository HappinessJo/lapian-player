> P7 ≤150ms、P9 ≤300ms、P8 ≥12fps 且每帧呈现）、P11 4K ≤1.5GB；
> 任务：[tasks.md](../../tasks.md) T7.4；缓存依据 [T7.2](T7.2-memory.md)、
> 拖动依据 [T2.9](T2.9-preview.md)/[T2.10](T2.10-drag-release.md)。

## 1. 结论

| 指标 | 4K 硬解（本文主结论） | 4K 软解（对照，不保证） |
|---|---:|---:|
| P4 拖动预览 | **60.8 / 61.0fps**（122/123 次 Present / 2s） | 60.1fps |
| P6 松手精确 p95 | **142.6 / 143.4ms** | 301.7ms（超 300） |
| P7 后退 p95（20 样本） | **1.86 / 1.67ms**（max 410/409ms，1/20 超） | 4.49ms（max 397ms） |
| P7 前进 p95（20 样本） | **4.34 / 4.40ms**（max 180ms，1/20 超） | 13.92ms（max 264ms） |
| P7 seek 后 PgUp / PgDn（单样本） | 213.3 / 0.32ms（PgUp 超 150） | 81.2 / 11.5ms |
| P8 长按 2s | **13.0 帧/秒，26 帧 / 26 次 Present** | 13.0 帧/秒，26/26 |
| P9 跳转 p95 | **225.4 / 226.8ms** | 320.6ms（超 300） |
| P11 播放 WS max | **140.1MB**（上限 1536MB） | 未单独测播放 |
| 步进时 WS 高水位 | 683.6MB（后退/前进各 40 步后） | — |

- **4K 硬解一轮 P4/P6/P7/P8/P9/P11 全部达到 spec 的 4K 放宽档**；数字来自 20 样本
  p95，硬解 `hw=1`（D3D11VA）在 `drag_begin` 日志中确认。
- **P7 的 p95 通过不等于“后退永不卡”**：4K 2s GOP 下一次缓存未命中约 **410ms**
  （解码 20–60 帧 + 20 帧硬件回拷），40 步扫描里出现 2 次；180 帧左右出现一次。
  p95 规则允许 1/20 超限，本文同时给出 max 与超限次数，不隐藏尖峰。
- **P7 “精确 seek 后紧接 PgUp”单样本 201–213ms > 150ms**：精确 seek 不预热后退
  缓存，PgUp 仍要从关键帧解起；PgDn 走顺序解码 0.32ms。这个单样本不冒充通过。
- **软解一轮 P6/P9 略超 300ms（301.7/320.6），按 spec 不作为保证档兜底**；
  软解 P7 p95 反而通过，是因为这份 4K 代理软解很快（探针 120 帧/840ms ≈ 200fps），
  不能外推到真实 V4 的复杂内容。
- 回归：`ctest` **21/21**（14.62s）；`--key-test`/`--loop-end-test`/`--mark-test`/
  `--snapshot-test`/`--index-test` 全部 exit 0；1080p 前进 p95 从 46.69ms 降到
  **0.36ms**、后退 p95 38.81ms（仍 <80ms）；`dist` **32.54MB / 25 文件**。

## 3. 方法

### 3.1 产品路径与测试开关

- P4/P6/P7/P8/P9 由 **测试专用** `--drag-test` 驱动（`src/app/DragTestRunner.cpp`）：
  打开文件并等异步索引就绪后，通过 `MainWindow` 的 ForTest 入口走到产品同一路径：
  - P9：`GoToFrame`（与输入帧号同一入口）20 个随机目标，只取“目标距前关键帧
    ≤2s（30fps 时 60 帧，按素材帧率换算）”的样本；
  - P6：`OnScrubStarted → OnScrubTargetChanged → OnScrubFinished`，即产品拖动预览
    → 松手精确；每次拖动有 48ms + 16ms 的预览窗口，再计松手耗时；
  - P7：先 `GoToFrame` 到目标，再发 PgUp×20 / PgDn×20；另测“精确 seek 后紧接
    PgUp/PgDn 各一次”；
  - P8：`PressKeyDown(PageDown)` 保持 2s 后松开，统计帧数/秒与 `GfxWidget`
    真正 Present 的次数（`MainWindow::framePresented`）；
  - P4：拖动中每 16ms 更新一次目标、持续 2s，统计拖动期间实际 Present 的帧数。
- **P4 的帧率是“产品路径 Present 的预览帧数 / 拖动时长”**，不是解码器探针；
  预览解码器本身是独立的软件解码 + 最长边 1280 降采样（T2.9 语义未改）。
- `--force-software-decode` 只设置 `LAPIAN_FORCE_SOFTWARE=1`，
  `VideoDecoder` 跳过 D3D11VA、直接开软解；产品默认仍是硬解优先、失败回退软解。
  `drag_begin hw=` 打印实际解码器（1=D3D11VA，0=software）。
- `--memory-test`（T7.2）继续用于 P11 与 40/200 步 p95，命令见 §3.3。
- 诊断日志（默认关闭，只影响日志）：
  - `LAPIAN_SEEK_LOG=1`：每次 seek 打印 hit / keyframe / decoded / seek_ms /
    decode_ms / cache_ms；
  - `LAPIAN_STEP_LOG=1`：每步打印 frame→frame、ms；
  - `LAPIAN_PUT_LOG=1`：每次缓存回拷打印 transfer_ms / total_ms / evicted。

### 3.2 样本与阈值

- 每个 p95 指标 **20 个样本**；P7 后退/前进各 20 步，另有 seek 后 PgUp/PgDn 单样本。
- 4K 阈值：P4 ≥20fps、P6 ≤300ms、P7 ≤150ms、P9 ≤300ms、P8 ≥12fps 且
  Present 次数 ≥ 帧数；1080p 对照阈值：P4 ≥30fps、P6 ≤150ms、P7 ≤80ms、P9 ≤200ms。
- p95 索引口径与其他 perf 文档一致：排序后 `floor((n-1)*0.95)`；n=20 时是第 19 个
  （允许 1 个超限），n=40 时是第 38 个（允许 2 个超限）。
- P6/P9 的目标都检查了“距前关键帧 ≤2s”的前提；`p9_prefix_max` 会写进 summary。

## 4. 基线：228ms 可复现，根因是两处

T7.2 记录 4K 40 次后退 p95 **228.09ms**。本轮先用同一 `--memory-test step` 复现
（`LAPIAN_SEEK_LOG`/`LAPIAN_STEP_LOG` 打开）：

| 场景 | 基线（本轮复现） | T7.2 记录 |
|---|---:|---:|
| 4K 后退 40 步 p50 / p95 / max | 0.77 / **259.43** / 334.12ms | 0.60 / 228.09 / 313.61ms |
| 4K 前进 40 步 p50 / p95 / max | 140.55 / **230.02** / 247.15ms | 141.87 / 231.68 / 248.91ms |
| 缓存命中 / 未命中 | 35 / 5（窗口 8 帧） | 35 / 5 |

分项日志（`LAPIAN_SEEK_LOG`）显示两个独立问题：

1. **前进每次都在重解整段**：`GoToFrameForStep` 前进步进传 `kNone`，而
   `MediaSession::SeekToFrame` 无条件 seek 到最近关键帧再解码到目标。4K 2s GOP
   下每步解 20–60 帧，日志里 `decoded=22/23/24...`、decode_ms 25–170ms。
2. **后退每 8 步重新从关键帧解一次**：8 帧窗口（96MiB）只能覆盖 8 步，
   第 9 步未命中；未命中的成本不是解码（decode_ms 25–172ms），而是
   **硬件帧回拷**：`FrameCache::Put` 每次 4K 回拷约 11ms/帧，一次未命中要回拷
   8 帧；`LAPIAN_PUT_LOG` 显示每批**第一帧 88ms**（等 GPU 解码队列排空）、
   其余 11ms，合计约 **160ms**，与 GOP 距离无关。
   典型未命中：`frame=299 decoded=60 seek_ms=0.33 decode_ms=171.74
   cache_ms=161.65 total_ms=333.74`。

## 5. 改动（`40bba7f`）

| 改动 | 说明 |
|---|---|
| 前进步进走顺序解码 | `MediaSession` 增加 `sequential_frame_`：解码器正好停在目标帧时，`SeekToFrame(kNone)` 只调一次 `DecodeNextFrame`；缓存命中/重新 seek/开文件/装索引都会使顺序位置失效。前进 4K p95 230ms → **4.12ms**。 |
| 4K 后退窗口 8 → 20 帧 | `FrameCache::LimitsForFrame` 的 4K 档从 `96MiB/8` 改为 `256MiB/20`。仍只缓存“后退步进解码到目标前的软件 NV12 帧”，普通跳转/前进/播放不写缓存，播放期缓存为空（P11 不受影响）。40 步扫描未命中 5 → 2 次。 |
| 测试专用入口 | `--drag-test`（P4/P6/P7/P8/P9，20 样本，产品路径）、`--drag-samples`、`--drag-tag`、`--force-software-decode`；`LAPIAN_SEEK_LOG`/`LAPIAN_STEP_LOG`/`LAPIAN_PUT_LOG`。 |
| 单测 | `frame_cache_test` 更新 4K 预算断言 + 超大帧回退；`media_session_test` 增加“顺序前进/后退命中缓存仍帧精确”。 |

不做的事：不改产品默认硬解/回退逻辑，不改 B 到达/显示尺寸，不改拖动预览语义，
不降质/丢帧，不放宽阈值。

## 6. 4K 硬解结果

### 6.1 40 步步进（`--memory-test step`，两轮）

| 轮次 | 方向 | p50 | p95 | max | 超 150ms | 命中/未命中 | WS max |
|---|---:|---:|---:|---:|---:|---:|---:|
| opt 1 | 后退 | 0.68 | **2.00** | 415.82 | 2/40 | 38/2 | 683.6MB |
| opt 1 | 前进 | 0.45 | **4.12** | 27.94 | 0/40 | — | — |
| opt 2 | 后退 | 0.61 | **1.76** | 420.58 | 2/40 | 38/2 | 683.2MB |
| opt 2 | 前进 | 0.33 | **4.15** | 27.49 | 0/40 | — | — |

- 缓存 `count=20 bytes=248,832,000 max_bytes=268,435,456 max_entries=20`；
  20 帧未命中后命中 18–19 步，`evictions` 只在窗口滚动时发生。
- **两处尖峰是真实成本**：`frame=299 decoded=60 decode_ms=120.63
  cache_ms=294.54 total_ms=415.49`、`frame=279 decoded=40 decode_ms=28.25
  cache_ms=295.11 total_ms=323.98`。缓存回拷 20 帧 ≈ 295ms（首帧 88ms + 19×11ms），
  这段无法用“丢帧/降质”消掉；本文把它作为 4K 可用档的已知尖峰记录。
- 步进高水位 683.6MB 是“缓存 249MB + 解码器/堆”的峰值，**不是 P11**；
  P11 口径是播放（见 6.3）。

P7 的两个“尖峰”说明：

- 后退方向的 410ms 尖峰是**第一样本**（精确 seek 后第一次 PgUp）——它同时就是

- 前进方向的 180ms 尖峰是**第一样本**：后退 20 步后解码器位置失效，第一次

- 额外的 seek 后单样本（不参与 p95）：PgUp **213.30 / 200.99ms**（超 150），
  PgDn **0.32 / 0.34ms**。PgUp 超限的原因是精确 seek 不预热后退缓存；
  若为它预热 20 帧，P9 4K 会被回拷成本推到 300ms 以上，因此没有做，
  如实记录为缺口（见 §9）。

|---|---:|---:|---|
| P4 预览 fps | 60.1（121 Present / 2.01s） | ≥20 | 过 |
| P6 松手 p50 / p95 / max | 153.38 / **301.66** / 355.85 | ≤300 | **未过（2/20 超）** |
| P7 后退 p50 / p95 / max | 3.57 / 4.49 / 397.30 | ≤150 | p95 过（1/20 超） |

| P7 seek 后 PgUp / PgDn | 81.18 / 11.50 | ≤150 | 过（单样本） |
| P8 帧/秒 / Present | 13.0 / 26 帧 26 次 | ≥12 | 过 |

- 软解 P7 能过，是因为这份 4K 代理软解很快（`lapian_decode_probe --sw` 120 帧

## 9. 缺口 / 不宣称

1. **不是正式 V4**：素材是 15s/450 帧的 4K 代理（简单合成内容），不是 spec §8
   的 V4 真片；P4 的 60fps 与软解速度都可能因真实内容下降。
2. **不是基线机**：6C/12T + RTX 4060 + 32GB，明显强于 4C/8GB/集显。
3. **不是冷缓存**：没有清 Windows 文件缓存/重启；首次打开可能更慢。
4. **P7 的 p95 通过但尖峰仍在**：4K 2s GOP 下每约 20 步出现一次 ~410ms 的
   缓存重填；这是 4K 可用档的真实成本，不写成“后退无卡顿”。
5. **“精确 seek 后紧接 PgUp”单样本 201–213ms 超 150ms**：seek 不预热后退缓存；
   为它预热会推高 P9 4K，当前不修，列入后续（若 T7.7 认为必须，需重新权衡
   P9 与 P7 的取舍）。
6. **软解 P6/P9 未过**：301.66/320.61ms；按 spec 软解不作为保证档兜底。
7. **P4 的 60fps 是“预览 Present 帧率”**：代理软解很快；真实 4K 复杂内容
   可能低于 60fps，是否有 20fps 需 V4 复测。
8. **P5/P3 未重测**：P5（10s 往返无 >200ms 停顿）是 T2.10 的 1080p 结论；
   P3（Begin→首帧）是 T2.9 的 31ms。本文没有 4K P5/P3 的 20 样本数字。
9. **P11 只测 15s**：4K 素材只有 15s；没有 2h 4K 长跑，也没有 GPU 显存统计。
10. **未测**：真实 V4/V5、H.265 4K、10-bit/HDR 4K、多显示器/200% 缩放、
    RDP/集显、冷启动 P1/P2 的 4K 组合；这些都留 T7.7。
11. 不把本文写成 P14/V10/基线机/正式 V4 通过；T7.3 仍只等 V10 2h。

## 10. 复现注意

- 多个 GUI 测量不要并行跑；本文数字是逐进程串行采样。
- `--drag-test` 走异步索引，等 `IndexReadyForTest` 后才开始；P6 的拖动有真实
  预览窗口（48ms + 16ms），不是纯同步调用。
- `--force-software-decode` 只影响本进程；不设置时产品仍硬解优先。
- 4K 2s GOP 的 `--memory-test step` 从第 300 帧开始后退 40 步（300 是 proxy 的
  关键帧），第一次后退会跨整个 GOP，适合作为最坏情况。
- 日志是 UTF-8；PowerShell 控制台 GBK 时用 `ReadAllBytes + UTF8.GetString`。
