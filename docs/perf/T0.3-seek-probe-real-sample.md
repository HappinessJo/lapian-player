# T0.3 真实素材补测（短 GOP vs 长 GOP，2026-10-19）

- **状态**：初步补测；**不是 V1/V3/V4 的正式结论**。
- **素材**：用户提供的 `media\测试.mp4` + 由它派生的 2s GOP / 长 GOP 压力变体（30s 与全长）。
- **目的**：在真实画面上隔离“GOP 长度”对 P6/P7 的影响，避免只用 testsrc2 代理下结论。
- **结论先行**：同一真实内容，短 GOP（30）硬解 p95 **28.08ms**；改成 GOP 250 后硬解 p95 **230.47ms**。
  GOP 是决定性变量，落点仍全部精确。

## 1. 素材

| 素材 | 来源 | 规格 |
|---|---|---|
| `media\测试.mp4` | 用户提供，真实 1080p H.264（V2 类，30fps） | 1920×1080，H.264，30fps，152.43s，4573 帧，AAC 48kHz 立体声，CFR，**GOP 30（约 1s）**，约 10.1Mbps |
| `build\test-media\real-longgop.mp4` | 由上一文件前 30s 重编码，仅压力测试 | 1920×1080，H.264，30fps，30s，**GOP 250（约 8.3s）** |
| `build\test-media\real-gop2s-full.mp4` | 全长重编码，2s GOP 阈值验证 | 1920×1080，H.264，30fps，152.43s，**GOP 60（2s）** |
| `build\test-media\real-longgop-full.mp4` | 全长重编码，仅压力测试 | 1920×1080，H.264，30fps，152.43s，**GOP 250（约 8.3s）** |

长 GOP 变体用 `-g 250 -keyint_min 250 -sc_threshold 0`；2s 阈值变体用 `-g 60`。
`测试.mp4` 不是 V1：V1 要求 24fps，它是 30fps；但它是真实的 1080p H.264 画面，
可用于回答“真实内容 + 短/长 GOP 的差距”。

## 2. 方法

- 命令：`scripts\measure\seek-probe.ps1`，硬解 D3D11VA + 软解各一轮。
- 主口径 **20 样本**（spec §4.1 的 p95 定义）；另做 **40 样本**复核，确认 p95 不靠样本运气。
- 每个样本：关键帧回退 → 解码到目标 PTS；不渲染、不拷贝、不缓存。
- 因此结果是**冷 seek 下界**；产品 P6/P7 还有拖动预览预热、精确 seek 路径缓存与呈现开销，
  不能用探针单独定产品 P6/P7 的最终结论。

## 4. 判读

1. **短 GOP 真实素材，硬解通过 P7/P6/P9 的下界**：
   20 样本 p95 26.59ms、40 样本 p95 28.08ms，远低于 P7 80ms、P6 150ms、P9 200ms。
2. **2s GOP 是 P6/P9 的可行门槛，但对 P7 太紧**：
   40 样本硬解 p95 **76.06ms**；对 P6 150ms / P9 200ms 有余量，
   对 P7 80ms 只剩 3.94ms，说明随机 seek 的 P7 不能靠 2s 门槛硬扛。
3. **GOP 250 硬解 p95 230.47ms**：
   P7（≤80ms）与 P6（≤150ms）都超；P9（≤200ms）也在 p95 上超。
   落点仍然 40/40 精确，说明“帧准确”没有被牺牲，超的是延迟。
4. **GOP 是决定性变量，不是合成画面的问题**：
   同一内容、同一编码器、只改 GOP，40 样本 p95 从 28.08ms（1s）→76.06ms（2s）→230.47ms（8.3s）。
5. **软解不能作为保证档兜底**：
   短 GOP 软解 p95 136.01ms 已超 P7；2s GOP 软解 p95 321.05ms；
   长 GOP 软解 p95 944.97ms。保证档必须依赖硬解；硬解失败时只能按“可用档/降级”处理。
6. **不是基线机**：本机 RTX 4060；spec 基线是 4C/8G/集显，正式数字仍需基线机复测。

## 5. 对 P6/P7 决策的含义

- 用户目前唯一真实素材是**短 GOP（1s）**；短 GOP 在硬解下满足当前 P7/P6/P9。
  如果片库以短 GOP 为主，“限制保证档 GOP”比“放宽指标”更贴近事实，且能保留 80/150/200ms。
- 2s GOP 的硬解 p95 是 76.06ms：**P6/P9 的 2s 门槛有数据支撑**（对 150/200ms 有余量）；
  但 P7 80ms 只剩 4ms 余量，所以 P7 应改成“±1 + 缓存/预取”，不能继续按随机 seek 考核。
- 长 GOP 变体证明：只要 GOP 到 250，1080p H.264 的随机冷 seek p95 就是 230ms 量级，
  P7/P6 物理不可达；P9 的 200ms 也不够。这个结论不依赖 testsrc2 内容。
- 现在只有 **1 个**真实文件 + 派生变体，不能代表片库分布；正式结论仍需
  V1（24fps）、V3（HEVC 60fps）、V4（4K 30fps）至少三条真实素材。
- 产品 P6/P7 仍要在 T2.9/T2.10 用拖动预览 + 精确 seek 路径复测；探针只负责判“物理下界”。

## 6. 复现

```powershell
# 短 GOP 真实素材：20 / 40 样本
powershell -ExecutionPolicy Bypass -File scripts\measure\seek-probe.ps1 `
  -Files 'media\测试.mp4' -Samples 20 -Seed 1 -OutDir 'build\seek-tmp\real-test'
powershell -ExecutionPolicy Bypass -File scripts\measure\seek-probe.ps1 `
  -Files 'media\测试.mp4' -Samples 40 -Seed 1 -OutDir 'build\seek-tmp\real-test-40'

# 长 GOP 压力变体（仅测试用；编码器来自 third_party\tools\ffmpeg-gpl）
ffmpeg -ss 0 -t 30 -i media\测试.mp4 -c:v libx264 -preset veryfast -crf 20 `
  -g 250 -keyint_min 250 -sc_threshold 0 -pix_fmt yuv420p -c:a aac -b:a 96k `
  build\test-media\real-longgop.mp4
ffmpeg -i media\测试.mp4 -c:v libx264 -preset veryfast -crf 20 `
  -g 250 -keyint_min 250 -sc_threshold 0 -pix_fmt yuv420p -c:a aac -b:a 96k `
  build\test-media\real-longgop-full.mp4
ffmpeg -i media\测试.mp4 -c:v libx264 -preset veryfast -crf 20 `
  -g 60 -keyint_min 60 -sc_threshold 0 -pix_fmt yuv420p -c:a aac -b:a 96k `
  build\test-media\real-gop2s-full.mp4

powershell -ExecutionPolicy Bypass -File scripts\measure\seek-probe.ps1 `
  -Files 'build\test-media\real-longgop.mp4' -Samples 20 -Seed 1 `
  -OutDir 'build\seek-tmp\real-longgop'
powershell -ExecutionPolicy Bypass -File scripts\measure\seek-probe.ps1 `
  -Files 'build\test-media\real-longgop-full.mp4' -Samples 40 -Seed 1 `
  -OutDir 'build\seek-tmp\real-longgop-full'
powershell -ExecutionPolicy Bypass -File scripts\measure\seek-probe.ps1 `
  -Files 'build\test-media\real-gop2s-full.mp4' -Samples 40 -Seed 1 `
  -OutDir 'build\seek-tmp\real-gop2s-full'
```
