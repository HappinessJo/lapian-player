# T7.3 长时稳定性（浸泡监测）测量记录（2026-10-21）

> 验收口径：[spec.md](../../spec.md) §4.1 P14（2h 1080p 连续播放，内存 ≤1.2GB、无持续增长、不崩溃/卡死）、
> §4.4；任务：[tasks.md](../../tasks.md) T7.3。
> 本文是**开发机、暖文件缓存、152s 1080p 代理、整片 A/B 循环**的短时探针，
> **不是 V10 2h 素材、不是 P14 正式验收、不是基线机结论**。
> 正式结论留 T7.7；有 V10 后必须重跑 7200s。
>
> 原始日志（build 不入库，重跑即可再生）：`build\soak\probe1800-20261021-123534.log`、
> `build\soak\noaudio600-20261021-130917.log`、`build\soak\probe3600-*.log`。

## 1. 结论

- **T7.3 未通过**：30 分钟和 1 小时带音频探针都触发 `memory_growth`。
  30 分钟 WS **107.8 → 126.1MB**（+18.2MB，斜率 30.49MB/h）；
  1 小时 WS **105.6 → 126.4MB**（+20.8MB，斜率 21.42MB/h），最大 **129.9MB**。
- **换成 5 分钟下包络后仍然失败**：30 分钟 6 个块、最低水位 +15.3MB、
  斜率 27.12MB/h；1 小时 12 个块、最低水位 +19.2MB、斜率 21.19MB/h。
  说明不是“循环边界尖峰把线性拟合抬高”，而是**基线本身在缓慢抬升**。
- **1 小时里有一次持续台阶**：t=2460（第 16 次 B→A）WS 114.1→121.1MB、
  private +13MB、handles +20，之后 10 分钟没有回落；5 分钟块最低水位也从
  114.1 跳到 121.1/125.1。还需查是解码器表面池、D3D11 驱动分配还是音频设备
  重建；当前没有证据判断它会平台化。
- **不是崩溃/卡死/缓存泄漏**：30min/1h 全程 `cache_entries=0`、
  `audio_underruns=0`、`frame_stall_events=0`、`playback_stopped=0`，
  UI 心跳最大 298ms；句柄 673→680（max 707）、线程 55→50（max 60）。
- **10 分钟无音频对照**：`pass=1`，WS 97.7→103.9MB（+6.2MB），最大 123.2MB；
  只有 2 个 5 分钟块，下包络 +4.8MB（不足以判持续增长）。说明慢漂移不是
  音频路径独占，视频解码/渲染/堆也参与。
- **1 小时带音频探针**：`pass=0`，`flags=memory_growth`（详见 §4.3）。
- **30 分钟带音频复测（加 audio_state 观测 + LAPIAN_AUDIO_LOG）**：`pass=1`，
  WS **111.5 → 114.6MB**（+3.0），下包络 +4.0/8.85MB·h⁻¹；11 次 B→A；
  全程 `audio_state=playing`，**没有设备丢失/重连**；underrun 0、cache 0。
- **30 分钟无音频对照**：`pass=1`，WS **100.4 → 107.8MB**（+7.4），下包络
  +7.4/15.31MB·h⁻¹（接近 16MB/h 门槛）；11 次 B→A；cache 0。
- **35 分钟带音频复测（`probe2100`）**：`pass=1`，WS **110.0 → 114.8MB**
  （+4.8），下包络 +4.8/8.47MB·h⁻¹；13 次 B→A；`audio_state=playing`、
  cache 0、无卡顿。三次 30min 级探针（audio/+3.0、noaudio/+7.4、35min/+4.8）
  都通过，只有一次 30min（+18.2）和一次 1h（+20.8）失败。
- **定位结论（暂）**：慢漂移**不是每次音频循环必现**，也不是音频独占；
  同样 30min 一次 +18.2MB、一次 +3.0MB，存在明显运行间差异。更像是堆/
  解码器表面池/驱动分配在特定系统状态下抬升。1h 的 `pass=0` 仍是真实结果，
  不能因为一次 30min 通过就判 T7.3 通过；下一步需要 2h 或 V10 看是否平台化。
- **回归**：`ctest 21/21`（15.43s）；`--key-test` 77 项 0 失败（2s 长按 27 帧）；
  `--loop-end-test` V9/1080p/4K 分别 5/6/6 次 B→A、`playing=1`；
  `--index-test` 12 项 0 失败；`--memory-test pause/play` 87.8 / 105.4MB。
  `dist` **32.52MB / 25 文件**。
- **不宣称**：不是 V10、不是 2h、不是 P14 通过、不是基线机/冷缓存。
  T7.3 仍是**代码完成、验收未通过**；下一步要用 V10 跑 7200s 并定位慢漂移。

## 3. 方法

### 3.1 `--memory-mode soak`

```powershell
powershell -ExecutionPolicy Bypass -File scripts\soak-bench.ps1 `
  -File build\t7.2-media\test1080.mp4 -Seconds 1800 -Interval 30 -Tag probe1800
```

- 打开文件 → 等异步索引就绪 → A=0、B=last → 开循环 → 从 0 播放。
- 每 30s 采样：WS/private/peak/handles/线程数/帧号/playing/循环跳数/
  audio underrun/波形状态/帧缓存条目/UI 心跳间隔。
- 产品路径不变：异步索引、T7.2 缓存策略、T7.2.1 B 到达/显示尺寸都未改。
- **整片 A/B 循环**是为了让 152s 有限素材能持续播放；它不是“2h 单文件连续
  播放”，报告必须区分。

### 3.2 判定阈值

[`src/app/SoakStats.cpp`](../../src/app/SoakStats.cpp)：

| 项 | 口径 |
|---|---|
| 稳态窗口 | 2h 去前 60s；短时探针取 10%（最小 5s、最大 60s） |
| 内存上限 | 1080p 1200MB（P14 1.2GB）；4K 诊断用 1536MB |
| 持续增长 | 稳态样本按 **5 分钟分块取 WS 最小值**（下包络），对包络做最小二乘；包络斜率 >16MB/h **且** 首末包络增量 ≥12MB |
| 原始曲线 | 全窗口首末增量/斜率仍写入 summary（`growth_mb`/`slope_mb_per_h`），只做对照，不单独判失败 |
| 句柄/线程 | 末值 > 首值 +64 / +2 |
| 帧缓存 | 纯播放路径任何采样 `cache_entries > 0` |
| 播放中断 | 稳态采样 `playing=0` |
| 帧停顿 | 连续 ≥2 个采样窗口帧号不变且没有 B→A 回绕 |
| UI 卡死 | 心跳间隔 >2000ms；看门狗 10s 记录、30s `_Exit(6)` |

- 下包络的作用是忽略循环边界的瞬时分配尖峰；如果包络本身持续抬升，仍判增长。
- 斜率/增量门槛是“持续增长”的自动化口径，不是 P14 的替代；短时探针通过
  也不等于 2h 无增长。
- 音频 underrun 只记录，不判失败（设备恢复/拔出归 T7.5/T7.7）。

## 5. 慢漂移分析

1. **不是每循环固定泄漏一个句柄/线程**：handles 673→680、threads 55→50，
   无单调增长；`FrameCache` 全程 0；音频 underrun 0。
2. **锯齿+缓慢抬升**：30min 内出现三次 5–12MB 回落，最终又回到 126.1MB；
   1 小时里 t=2460 的 +7MB 台阶持续了至少 10 分钟。既有瞬时尖峰，也有
   基线抬升，单看某一段会误判。
3. **运行间差异很大**：同机同素材的 30min 带音频，一次 +18.2MB（`pass=0`），
   一次 +3.0MB（`pass=1`）；无音频 30min +7.4MB（`pass=1`，下包络 15.31）。
   这更像堆/驱动分配在特定系统状态下抬升，而不是固定的每循环泄漏。
4. **音频不是唯一原因**：`audio1800` 全程 `playing`、无 device lost/重连，
   仍可能涨；无音频也涨。不能只修音频循环重启。
5. **下包络仍失败**：30min 包络 +15.3MB/27.12MB·h⁻¹、1h 包络
   +19.2MB/21.19MB·h⁻¹，都超过 12MB/16MB·h⁻¹ 门槛；不是阈值把尖峰当增长。
6. **仍按失败处理**：在没有 2h 数据证明平台化之前，不把 `pass=0` 解释成通过，
   也不因为一次 30min `pass=1` 判 T7.3 通过。
7. **下一步**：用 V10 2h 跑 7200s；没有 V10 就用现有素材跑 2h 看是否平台化。
   若仍线性增长，再做堆/解码器表面池定位（ETW/UMDH，或分段禁用音频/渲染），
   不要在 T7.3 里用阈值掩盖。

## 8. 缺口 / 不宣称

1. **没有 V10 2h 素材**：最长只有 152s 1080p 代理；本文是循环短时探针。
2. **不是 P14**：30min 探针一次 `pass=0`、一次 `pass=1`，1h `pass=0`；
   慢漂移没有平台化证据，不能判通过。

5. **没有设备恢复/拔出**：音频 underrun 0 只代表本轮设备正常。
6. **没有真实 V1/V4/V10、4K 长跑、0.25x 长跑**；归 T7.4/T7.7。
7. 不把本文写成 P14/V10/基线机/正式 P10/P11 通过。

## 9. 复现注意

- 用 `scripts\soak-bench.ps1`，不要直接 `Start-Process` 传中文路径；脚本会建
  ASCII 硬链接并做外部超时。
- 日志 UTF-8；Windows PowerShell 5.1 读日志用
  `[IO.File]::ReadAllBytes + [Text.Encoding]::UTF8.GetString`。
- 浸泡期间不要并行跑其他 GUI 回归，避免内存/线程/帧号采样被干扰。
- 30min/1h 的 `pass` 只代表自动阈值；`flags` 和 WS 曲线要一起看。
- 没有 V10 时，报告必须写“短时探针”，不能写 P14 通过。
