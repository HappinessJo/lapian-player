# T7.1 冷启动测量记录（2026-10-20）

> 验收口径：[spec.md](../../spec.md) §4.1 P1/P2（P1 ≤1.5s、P2 ≤2.5s，20 次至少 19 次）、
> §3.1 F1-A1；任务：[tasks.md](../../tasks.md) T7.1。
> 本文是**开发机**证据，不是基线机、正式 V1 或“清空 OS 文件缓存”的正式 P1/P2 结论；
> 正式结论留 T7.7。所有数字可用 `scripts/startup-bench.ps1` 重跑，原始 CSV 在
> `build/t7.1-final-bench-*/startup-samples.csv`（build 不入库）。

## 1. 结论

- **P1 20/20 达标**：三份素材 p50 255.5–257.1ms、p95 262.0–265.7ms，最差单次 368ms
  （系列第 1 次，冷 DLL/系统缓存），余量约 4–5.9 倍。
- **P2 20/20 达标**：proxy-V1 p50 **308.26ms** / p95 312.86ms；152s 1080p p50
  **319.39ms** / p95 336.11ms；4K proxy p50 **330.39ms** / p95 336.18ms。
- **索引后置是 P2 的关键改动**：152s 1080p 的索引从 696ms 打开路径里移走，改为首帧后
  后台扫描 374.3ms；同一素材 P2 从 696.11ms（同步单次）降到 319.39ms（p50）。
  2 小时片源的索引时长不再进入 P2，只影响“扫描中”的持续时间和 T7.2/T7.3 的资源预算。
- **启动预算**（p50）：进程→QApplication 17.5ms、MainWindow 构造 +10ms、
  `show()`（含 D3D11 设备/交换链/着色器）约 227ms、事件循环可交互 +1ms、
  打开→首帧 +52–75ms。**D3D11 初始化是 P1 的最大单项**，但 255ms 距 1.5s 余量足够，
  没有为了数字把设备创建挪到首帧之后（那会把同一段耗时变成“窗口先出来但视频区卡住”）。
- `ctest` **19/19**（13.89s）；`dist` **32.45MB / 25 文件**（P12 上限 100MB）。
- 新增回归：`--index-test`（扫描中 → 就绪 → 标记加载）12 项全过；
  `--startup-test` 只做测量，有 10s 超时保护。

## 3. 方法

### 3.1 埋点口径

`--startup-test` 在 main 最前面取 `steady_clock`，记录：

| stage | 含义 |
|---|---|
| `app_created` | `QApplication` 构造完成（Qt 平台插件已加载） |
| `window_created` | `MainWindow` 构造完成（控件树/设置加载/空态已建） |
| `window_shown` | `window.show()` 返回（Win32 窗口可见；GfxWidget 的 D3D11 设备/交换链在 showEvent 里建） |
| `ui_ready` | show 后事件循环第一次派发（窗口可见且能处理事件） |
| `open_begin` | 定时器调用 `OpenFile` 前 |
| `open_returned` | `OpenFile` 返回（异步模式下不含索引） |
| `first_present` | 视频帧真正 `IDXGISwapChain::Present` 成功（`GfxWidget::framePresented`） |

- **P1 = `ui_ready`**：进程启动→窗口可见且事件循环可交互。不是“首帧画面绘制完成”；
  本口径只证明窗口已能处理事件，不单独量空态首绘耗时。
- **P2 = `first_present`**：进程启动→首帧 Present。DWM 合成到屏幕的额外延迟没有单独测，
  与 T0.2 的呈现探针口径一致。
- 每行是独立进程；P1 无文件，P2 用 `--file`（与双击关联文件走同一个打开入口；
  文件关联本身在 T7.6）。

### 3.2 命令

```powershell
# P1 + P2 各 20 次，输出 CSV
powershell -ExecutionPolicy Bypass -File scripts\startup-bench.ps1 `
  -Exe dist\lapian.exe -File media\proxy\proxy-V1.mp4 -Runs 20 `
  -OutDir build\t7.1-final-bench-proxy
powershell -ExecutionPolicy Bypass -File scripts\startup-bench.ps1 `
  -Exe dist\lapian.exe -File media\测试.mp4 -Runs 20 `
  -OutDir build\t7.1-final-bench-1080
powershell -ExecutionPolicy Bypass -File scripts\startup-bench.ps1 `
  -Exe dist\lapian.exe -File media\proxy\proxy-V4.mp4 -Runs 20 `
  -OutDir build\t7.1-final-bench-4k

# 索引后置回归（扫描中 → 就绪 → 标记加载）
dist\lapian.exe --file media\测试.mp4 --file-b media\V9.mp4 --index-test `
  --settings-path build\t7.1-index-settings
```

### 3.3 冷缓存限制（重要）

spec §4.1 要求“重启后首次启动，且目标文件不在 OS 文件缓存”。本会话**没有**清空
Windows 文件缓存（无 RAMMap/管理员权限），因此 20 次样本是“新进程 + 暖文件缓存”：

- Qt/FFmpeg DLL 与素材在系列中已被预热；第 1 次样本仍包含冷 DLL 加载
  （proxy-V1 的 P1 第一次 368.00ms，之后 253–267ms）。
- 正式“冷缓存 + 重启后首次启动”的 P1/P2 只能在 T7.7 用基线机与清缓存流程测。
- 本文不把 308–336ms 写成“任意机器/任意片源均达标”，只说“开发机、暖缓存、
  上述素材、20/20 达标”。

### 4.3 分段预算（p50 / p95，ms）

| 阶段 | proxy-V1 | 1080p 152s | 4K proxy |
|---|---:|---:|---:|
| `app_created` | 17.6 / 19.0 | 17.5 / 18.4 | 17.3 / 18.5 |
| `window_created` | 27.6 / 28.6 | 27.4 / 28.1 | 27.2 / 28.3 |
| `window_shown` | 255.1 / 259.2 | 255.5 / 270.9 | 255.5 / 258.7 |
| `ui_ready` | 256.1 / 260.4 | 256.4 / 271.9 | 256.4 / 259.7 |
| `first_present` | 308.3 / 312.9 | 319.4 / 336.1 | 330.4 / 336.2 |
| 索引等待（后台） | 22 / 24 | 378（单次计时） | 51 / 52 |
| 索引耗时（后台） | 19.3 / 20.3 | 374.3（单次） | 49.7 / 51.1 |

解读：

- **P1 的 227ms 在 `show()` 内**（`window_created`→`window_shown`）：D3D11 设备创建、
  swapchain、shader 编译、首次 Present 清屏；`ui_ready` 只多 1ms。
- **P2 的增量 52–75ms** 是 `OpenFile` 的探测 + 解码器打开 + 首帧解码 + 上传，
  不含索引；索引在首帧后并行。
- 首帧上传本身（`first_upload_ms`）0.17–0.31ms；音频/波形线程启动各 <0.1ms。

### 4.4 索引后置前后

同步索引是 T7.1 修改前的基线（单次样本，只用于说明成本位置）：

| 素材 | 帧数 | 同步 P2（单次） | 异步 P2 p50 | 后台索引 p50 |
|---|---:|---:|---:|---:|
| proxy-V1 | 720 | 425.49ms | 308.26ms | 19.25ms |
| 1080p 152s | 4573 | 696.11ms | 319.39ms | 374.30ms |
| 4K proxy | 450 | 376.05ms | 330.39ms | 49.66ms |

- 1080p 的索引速率约 **12.2k 帧/s**（4573/0.3743s）；按此线性外推，2 小时 30fps
  ≈ 216k 帧 ≈ 17.7s（**外推，不是 V10 实测**）。这条成本现在只影响“扫描中”的时长，
  不影响 P2。
- `--index-test` 观测（1080p）：
  - 扫描中：`ready=0 scanning=1 frames=0 nav=0 timeline=0 total=1`（扫描中），
    InfoBar 总帧显示扫描中；
  - 就绪：`ready=1 scanning=0 frames=4573 nav=1 timeline=1 total=3`（精确），
    标记在索引完成后从 sidecar 加载（V9 `count=1`）；
  - 扫描中 `CurrentFrame=0`，时间轴禁用，避免拖动到无法精确落帧的位置。

## 5. 实现

- `src/app/main.cpp`：`--startup-test` 埋点与退出条件；`--index-test` 回归；
  `--startup-test` 有 10s 超时（exit 3），打不开文件 exit 2。
- `src/app/GfxWidget.*`：`SetVideoFrame` 置 `present_pending_`，`Present` 成功后发
  `framePresented`（锁外发信号）；`MainWindow` 转发给 main。
- `src/media/MediaSession.*`：`Open(..., bool build_index)` 拆分；
  `InstallIndex` / `BuildIndexNow`；`MediaOpenTimings` 记录 probe/decoder/first frame/index。
- `src/media/FrameIndex.*`：`BuildFromFile(..., const std::atomic<bool>* cancel)`
  每包检查取消；取消返回 false 且不留下半成品索引（`lapian_frame_index_test` 新增 3 条断言）。
- `src/app/MainWindow.*`：索引线程（`std::thread` + generation + cancel + join）、
  `BeginIndexScan`/`ApplyIndexState`/`ApplyIndexFailed`；扫描中 `SetTotal(Scanning)`、
  禁用导航/时间轴/标记；就绪后 `SetTotal(Exact/Estimated)`、加载标记、创建预览器。
  VFR 仍按 T6.5 口径显示“扫描中”，不因索引完成改写总帧语义。
- 旧 GUI 回归（`--key-test`/`--mark-test`/...）通过 `SetIndexSynchronousForTest(true)`
  保持“打开后立即可导航”的既有语义；产品路径与 `--startup-test` 走异步。
- `scripts/startup-bench.ps1`：20 次 P1/P2、CSV、p50/p95、19/20 判定；后续 T7.8 可复用。

## 7. 缺口 / 不宣称

1. **不是冷缓存**：没有清 OS 文件缓存、没有重启后首次启动；见 §3.3。
2. **不是正式 V1/V7/V10**：V1 是 3–10 分钟真实 1080p 片，本机只有 152s 1080p 与代理；
   2 小时索引时长是外推。
3. **不是基线机**：6C/12T + RTX 4060 + 32GB，明显强于 spec 基线（4C/8GB/集显）。
4. **不是文件关联验收**：P2 用 `--file` 模拟关联入口，ProgID/双击在 T7.6。
5. **D3D11 未懒初始化**：P1 的 227ms 主要是设备/交换链；当前 5.9 倍余量下不值得把
   它挪到首帧后（会变成“窗口可见但视频区卡住”）。若基线机 P1 接近 1.5s，再单独评估。
6. **索引线程 join 在关窗/切文件时执行**：`FrameIndex` 每包检查取消，本地盘毫秒级返回；
   网络盘/卡死的 `av_read_frame` 仍可能拖慢关窗，归 T7.5 鲁棒性。
7. **VFR 总帧数仍显示“扫描中”**：这是 T6.5 的既定语义（帧号按显示帧计数），
   不是 T7.1 遗漏。
8. **未做真人/真实 4K VFR/HDR、200% 真实显示缩放、多显示器**；这些归 T7.7。
9. 不宣称 P1/P2 在基线机、正式 V1、冷缓存下通过；不把本文数字写成 F1-A1 正式验收。
