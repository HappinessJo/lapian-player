# T0.3 精确 seek 探针报告（P6/P7 Go/No-Go）

- **日期**：2026-10-19
- **任务**：T0.3 精确 seek 性能探针（tasks.md M0）
- **探针**：`src/tools/seek_probe/main.cpp` → `build\release\bin\lapian_seek_probe.exe`
- **调度**：`scripts/measure/seek-probe.ps1`
- **结论**：**长 GOP 素材下 P6/P7 不达标（初步 No-Go）**；需要规格决策或换缓存策略，不能靠 UI 掩盖。**正式结论仍待 V1/V3/V4 真素材复测。**
- **2026-10-19 补测**：真实 1080p30 短/长 GOP 对比见 [T0.3-seek-probe-real-sample.md](T0.3-seek-probe-real-sample.md)（短 GOP p95 28.08ms；2s GOP 76.06ms；8.3s GOP 230.47ms）。

## 1. 测量方法

对每个文件随机取 20 个目标帧（固定 seed），每个样本：

1. 由帧号算目标 PTS（CFR：`start + N/fps`）；
2. `av_seek_frame(AVSEEK_FLAG_BACKWARD)` 退到 ≤目标 PTS 的最近关键帧；
3. flush 解码器，逐包解码直到某帧 PTS ≥ 目标 PTS；
4. 记录“seek + 解码到目标帧”的墙钟时间与落点帧差。

硬解走 D3D11VA（`d3d11va2`，`AV_PIX_FMT_D3D11`），软解对照；先做一次预热 seek 丢弃。
**探针不渲染、不拷贝、不呈现**，因此结果是 P6/P7 的**下界**（产品只会更慢）。

GOP 分布由只 demux 的关键帧 PTS 差计算（单位：帧）。

## 4. Go/No-Go

| 素材 | 目标 | p95 | 判定 |
|---|---|---|---|
| 1080p H.264（GOP 250） | P7 ≤80ms / P6 ≤150ms | 275ms | **No-Go**（两项都超） |
| 1080p HEVC（GOP 120） | P7 ≤80ms / P6 ≤150ms | 63ms | 下界通过 |
| 4K H.264（GOP 60） | P7 ≤150ms / P6 ≤300ms | 259ms | P7 **No-Go**；P6 下界通过 |

**判读**：

- 长 GOP 是决定性变量：每退一个关键帧，平均要多解 `GOP/2` 帧；1080p 硬件解一帧约 1ms（含 demux/send/receive），GOP 250 平均要解 125 帧 → 与实测 125ms 吻合。
- HEVC 60fps 的 GOP 120 能过 P7，说明“解码器热、GOP 短”时预算够用。
- 4K 的 P7 150ms 在 GOP 60 下仍超（259ms），4K 的像素量放大了单帧成本。
- 探针是下界：加上 D3D11 呈现、纹理拷贝与 UI 帧调度后只会更慢，因此上述“不达标”是硬结论，“通过”还需要产品级复测。

**与 P9 的矛盾**：P9（输入帧号跳转）≤200ms 比 P7（随机单步）≤80ms 更宽松，但两者做的是同一次随机 seek。探针显示 1080p 长 GOP 下两者都会超，建议一并处理。

## 5. 需要决策（plan.md R1）

1. **限制保证档 GOP**：例如保证档要求关键帧间隔 ≤2s（H.264/HEVC），超出的素材归可用档。改动 spec §4.2，最贴近物理事实。
2. **放宽 P6/P7**：例如 P7 对“随机距离”放宽到 250ms，而 `±1` 步进靠帧缓存维持 ≤80ms；需要改 spec §4.1 与 tasks。
3. **改缓存策略**：帧缓存 + 前向预取能让 `±N`（N≈16–24）内的步进接近 0ms，但**不能**让任意远跳变快；单独用它解决不了 P7 的“随机距离”。
4. **组合（推荐）**：限制保证档 GOP + 帧缓存/预取；P7 拆成“±1 步进 ≤80ms（缓存保证）”与“随机距离步进按 P9 的 200ms”。

在决策前不进入 M2；先补 V1/V3/V4 真素材复测，确认代理结论。
