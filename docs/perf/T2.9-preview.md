# T2.9 拖动预览解码测量（2026-10-20）

- **状态**：开发机探针 + 真实窗口手测，**不是基线机 P3/P4/P5 验收**；正式数字待 T7.4/T7.7。
- **范围**：T2.9 拖动预览解码器（独立线程、独立解封装/解码、关键帧 seek、latest-frame、降采样）。
- **代码**：`src/media/PreviewDecoder.*`，由 `MainWindow` 在拖动期间以 16ms 定时器取最新帧。
- **测试**：`build\release\Release\lapian_preview_decoder_test.exe`（ctest 名称 `lapian_preview_decoder_test`）。

## 1. 环境与素材

| 项 | 值 |
|---|---|
| OS | Windows 11 x64 10.0.26200 |
| CPU/GPU | 开发机（RTX 4060）；**不是** 4C/8G/集显基线机 |
| 素材 | `media\proxy\proxy-V1.mp4`，1920×1080，720 帧，24fps（预览降到 1280×720 左右） |
| 预览路径 | 软件解码 + swscale 降到最长边 1280，NV12 |
| 解码器 | FFmpeg 7.1.1 最小构建 |

软件预览而不是硬件预览，是为了避开“精确解码器 + 预览解码器同时使用同一个 D3D11 设备/立即上下文”的并发风险；预览帧上传到 GPU 的尺寸已降到约 1280×720。

## 2. 方法

`lapian_preview_decoder_test`：

1. 建 `FrameIndex`，`Configure` 后在后台打开预览解码器；记录打开耗时。
2. 预热完成后 `Begin(600)`，以 1ms 轮询首张预览帧，记录 **Begin → 首帧**。
3. 模拟 2s 拖动：每 16ms 更新一次目标帧，在每次 16ms 窗口内取走最新帧，统计发布帧率。
4. 运行 3 次；下表给范围。

这是解码器探针，不含 `GfxWidget` 上传/合成和真实鼠标事件；真实窗口手测见 §4。

## 3. 结果

| 指标 | 3 次范围 | 说明 |
|---|---:|---|
| 后台打开 | 11.0–19.8ms | Configure → IsReady；不阻塞 UI |
| Begin → 首张预览 | **30.9–31.7ms** | 预热后；对应 P3 的预览部分 |
| 2s 拖动发布帧率 | **49.4–53.3fps** | 每 16ms 换目标 + 1ms 轮询 |

代表性单次：

```text
[perf] preview_open=19.779ms
[perf] first_preview=31.650ms
[perf] preview_fps=49.39 (100 frames / 2.025s)
```

即使把“打开 + 首帧”相加，开发机上也在 ~50ms 内；远低于 P3 的 100ms。P4 在 proxy-V1 上超过 30fps。

## 4. 真实窗口手测

用 `proxy-V1.mp4`：

- 拖动从第 56 帧到第 506 帧，拖动中信息栏/播放头为 506，画面已经显示预览帧 506；松开后精确到 506。
- 预览帧明显比精确帧“软”（1280×720 降采样），符合“拖动中降质预览”的语义。
- 拖动期间没有黑帧；旧预览帧不会在松手后覆盖精确帧（松手先停预览、清空 mailbox，再走精确 seek）。

截图：[拖动中的预览帧](T2.9-preview-mid.png)。

## 5. 判读与限制

1. **P3/P4 初值通过**：开发机 Begin→首帧 ~31ms、发布 ~50fps；但这是解码器探针，不是产品完整路径。
2. **P5 未正式测**：预览解码在独立线程，UI 只做 16ms 轮询与降采样帧上传；10s 往返拖动无 >200ms 停顿仍待 T2.10/T7。
3. **未覆盖 V1/V4/4K/基线机**：4K 软件预览可能低于 30fps；spec 的 4K 放宽档是 ≥20fps，仍需 T7.4 实测。
4. **未覆盖音频**：T3 之后才评估预览与音频时钟/静音的完整交互。
5. 预览解码器打开失败时只影响拖动预览，松手/步进/输入仍走精确路径；当前不在 UI 弹错误。
6. 预览帧最长边 1280 是开发期默认值，不是 spec 指标；若 4K 预览不达标，T2.10/T7 可调预算或下采样策略。
