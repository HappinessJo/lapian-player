# T2.9.1 反向拖动预览修复记录

- **日期**：2026-10-20
- **范围**：拖动预览反向（时间轴倒拖）频闪；T2.9 预览解码器的补丁，不改松手精确落帧
- **机器**：开发机 Windows 11 x64 / RTX 4060；**不是**基线机
- **代码**：`9242b6f`（fix: 反向拖动预览只发布目标帧并加小缓存）
- **单测**：`ctest` **18/18**（约 14.16s；`lapian_preview_decoder_test` 5.68s）
- **分发**：`dist` **32.34MB / 25 文件**
- **复现素材**：`media\测试.mp4`（复制为 ASCII 路径）、`build\t6.3-key\A.mp4`（60s / 24fps / `-g 24`）、`media/proxy/proxy-V1.mp4`

## 1. 根因

1. `PreviewDecoder::Process()` 的 `can_continue` 只在 `target_pts > last_pts_us` 时继续向前解码；
   反向目标永远 false，于是每个鼠标事件都从目标前关键帧重新 seek。
2. 解码循环对**每个中间帧**调用 `Publish()`。反向拖动时实际发布的是
   `keyframe…target` 的正向序列，鼠标继续回退又重新来一遍，画面表现为向前冲/频闪。
3. `UpdateTarget()` 只递增 generation，不清理 `latest`；`TakeLatestFrame()` 也不校验目标。
   目标 120→119 时，上一轮为 120 发布的帧仍可能被 16ms tick 取走，出现前后两帧闪。
4. 前向拖动因 `can_continue` 为真，发布序列单调递增且接近目标，所以看起来正常。

旧 `preview_decoder_test` 只做 `(target+7)%720` 的混合序列，没有断言反向发布帧的
单调性和目标精确性，因此 18/18 没有覆盖这个路径。

## 2. 修复

- `PreviewFrame` 增加 `pts_us/frame_index/generation`；`TakeLatestFrame()` 返回该结构。
- `UpdateTarget()` 记录方向（新目标更小 → backward），并立即丢弃比新目标更靠后的
  `latest`。
- **反向拖动只发布目标帧**：仍从关键帧向前解码（H.264 不能反向解），但中间帧只进缓存、
  不发布；到 `pts_us >= target_pts` 才发布一次。
- `TakeLatestFrame()` 双重过滤：比当前目标靠后的帧丢弃；反向模式下只接受正好是当前
  目标的帧。
- **32 帧预览缓存**（只存 1280 长边降采样 NV12，约 44MB @720p；`End/Close` 释放）：
  反向小步先在缓存里找目标帧，命中直接发布；未命中再 seek 解码并填充缓存。
  这不是 T7.2 的正式 LRU，不缓存全分辨率。
- `Begin()` 先只发布起点目标帧，避免按下时从关键帧向前冲一段；前向拖动后续仍保留
  中间帧发布，维持原预览帧率。
- 松手路径未改：`OnScrubFinished` 仍 `End()` + 精确 `GoToFrame(target)`。

## 3. 结果

`lapian_preview_decoder_test` 新增：

- 起点 600 必须发布 600；
- 反向 600→560 每步等到目标帧，断言 `frame_index == target` 且单调不增；
- 反向后向前一步 561 仍能到目标；
- 快速反向：目标每 16ms 退 1 帧、900ms，发布帧不得向前跳。

三份素材：

| 素材 | 首目标预览 | 前向预览 | 反向 40 步 | 快速反向 900ms |
|---|---|---|---|---|
| `proxy-V1`（长 GOP） | 583ms | 58.5–62.7fps | 1.58–1.64s / 39–41ms 每步 | 28 帧（约 31fps） |
| `build\t6.3-key\A.mp4`（60s，GOP 24） | 15.0–15.5ms | 64.4fps | 709–728ms / 17.7–18.2ms 每步 | 28 帧（约 31fps） |
| `测试.mp4` 副本（短 GOP） | 30.7–31.4ms | 58.1–59.4fps | 1.01–1.02s / 25.4–25.6ms 每步 | 28 帧（约 31fps） |

- “反向 40 步”是测试按每步等待目标帧统计，包含首次目标解码；不是鼠标 16ms 更新下的
  端到端帧率，也不是正式 P4/P3 验收。
- 关键行为：三种素材均通过“每步目标帧、单调不增、无向前跳、反向后前向恢复”。
- `测试.mp4` 的 H.264 解码器会打印大量 `missing picture in access unit` 错误日志（快速
  seek 的已知噪声），不影响断言；预览线程已把日志级别压到 error。

## 5. 结论与不宣称

1. **反向拖动频闪的根因已修**：反向只发布目标帧，过期帧被丢弃，缓存覆盖小步回退。
2. **不是正式 P3/P4/P9 验收**：数字是开发机、测试驱动器按步等待的探针；没有 20 样本
   p95、没有基线机、没有 4K。
3. **没有真人鼠标拖动/输入法验证**：`--preview` 单测直接驱动 `PreviewDecoder`；实际
   TimelineWidget 拖动、GfxWidget 呈现仍需手动确认一次。
4. **长 GOP 首次目标预览可能慢**：proxy-V1 起点 600 约 583ms；期间当前精确帧保持显示，
   不是黑屏。短 GOP 素材 15–31ms。
5. **缓存只覆盖 32 帧**：大幅反向跳转超出缓存仍要从关键帧重解，正确性不受影响，延迟
   可能超过 30ms；4K/长 GOP 未测。
6. **一次 snapshot 回归焦点 flake**：连续跑多个 GUI 测试时，`s-key-saved`/`s-focus-blocked`
   失败；单独重跑 exit 0。该测试依赖窗口焦点，和 PreviewDecoder 改动无直接关系，但说明
   回归脚本应逐个窗口串行并给焦点稳定时间。
