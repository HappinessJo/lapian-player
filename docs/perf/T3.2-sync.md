# T3.2 媒体时钟与音画同步测量记录

- **日期**：2026-10-20
- **范围**：`IAudioClock` 主时钟、QPC 回退、按媒体时间调度、落后丢帧
- **机器**：开发机 Windows 11 x64 / RTX 4060 / Realtek 默认输出；**不是** spec 的 4C/8G/集显基线机
- **代码**：T3.2 提交 `02bea9a`；构建 `scripts\build-release.ps1` 通过

## 1. 方法

- `LAPIAN_TIMING_LOG=1` 时，`PlaybackController` 每呈现一帧输出：
  `T3.2 sync_ms=<frame PTS - audio clock> frame=N target=T clock=audio|qpc`
- 每个 tick 只呈现“最接近 target 且未过期”的一帧；落后 >100ms 的旧帧丢弃，避免把多帧过期画面连续塞给 GPU。
- 统计 `|sync_ms|` 的 max / p95 / mean；一帧时长：24fps 41.67ms、30fps 33.33ms、60fps 16.67ms。
- 测试片：
  - `media/V9.mp4`（24fps，5s，AAC 48k 单声道）；
  - `build/sync60.mp4`（proxy-V1 循环 60s，24fps，AAC 48k 单声道）；
  - `build/sync30fps.mp4`（`media/测试.mp4` 截取 10s，30fps，AAC 48k 立体声）；
  - `media/proxy/proxy-V3.mp4`（60fps HEVC，20s，AAC 48k 单声道）；
  - `build/noaudio-V7.mp4`（无音轨，QPC 回退）。
- 测试片均只在本机 `build/`，不入库、不分发。

## 2. 设备时钟的关键坑

开发机 WASAPI shared mode 设备为 48kHz / 2ch / float32，`IAudioClient` 缓冲 1056 帧（约 22ms）。但 `IAudioClock::GetFrequency()` 返回 **384000**，不是 48000；即 `IAudioClock::GetPosition()` 的位置单位并不等于“采样帧”，必须用 `GetFrequency()` 换算秒，不能直接除以采样率。

如果按采样率换算，同一个流会把 0.42s 算成 3.7s（约 8–9 倍），视频会瞬间跳到中后段；这是 T3.2 实现中实际踩到并修正的问题。当前 `AudioEngine` 保存 `clock_frequency`，位置换算为：

```
media_seconds = anchor + (position - base) / clock_frequency
```

`base` 在第一次成功查询时捕获，不假设 Start 后位置一定为 0；若位置出现 >1s 的异常跳变，则重新锚定。

## 3. 结果

| 素材 / 场景 | 帧率 | 时长 | 呈现帧数 | max | p95 | mean |
|---|---:|---:|---:|---:|---:|---:|
| V9 | 24fps | 4s | 87 | 5.71ms | 4.98ms | — |
| sync60（proxy-V1 循环） | 24fps | 60s | 1439 | **9.33ms** | **4.68ms** | 2.13ms |
| sync30fps（测试片截取） | 30fps | 10s | 299 | 6.04ms | 4.42ms | 2.06ms |
| proxy-V3 | 60fps | 10s | 582 | 7.67ms | 3.67ms | — |
| noaudio-V7 | — | 3s | 65 | 4.43ms | — | — |

- 60s 24fps：max 9.33ms ≈ **0.22 帧**，p95 4.68ms；全程 `clock=audio`，60s 内无累积漂移。
- 30fps：max 6.04ms ≈ **0.18 帧**；最后一帧因音频先结束而 `clock=qpc`，属预期回退。
- 60fps：max 7.67ms ≈ **0.46 帧**，p95 3.67ms；每 tick 只提交最新帧，10s 内 582 帧。
- 无音轨：`clock=qpc`，max 4.43ms（QPC 与视频同源，数字小是预期的）。
- 60s 内音频设备位置与视频 PTS 无持续扩大趋势；未做 10 分钟正式 soak。
