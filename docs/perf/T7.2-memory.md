## 1. 结论

- **P10（打开后暂停 60s）**：1080p 152s 素材 **89.3MB** working set（p50 稳态 89.2MB），
  无文件空态 **63.8MB**；上限 250MB，开发机余量约 2.8 倍。
- **P11（播放）**：1080p 60s 播放最大 **106.0MB**（≤800MB）；4K proxy 播放最大
  **128.7MB**（≤1.5GB）。播放期间缓存为空，帧缓存不参与 P11。
- **帧缓存有界**：`FrameCache` 按字节 LRU。1080p 上限 64MiB/24 帧，实测 21 帧
  **65,318,400B**；4K 上限 96MiB/8 帧，实测 8 帧 **99,532,800B**；均未超上限。
- **后退步进命中缓存**：1080p 200 次后退 p50 **0.18ms** / p95 **32.72ms** / max 74.58ms，
  187/200 命中；前进步进 p95 **46.69ms**。1080p P7 的 80ms 在开发机代理上双向通过
  （不是正式 V1/P7 结论）。
- **4K 步进仍不满足 P7 的 150ms**：后退 p95 **228.09ms**、前进 p95 **231.68ms**；
  4K 路径留 T7.4，不把本文数字写成 P7 4K 通过。
- **切文件释放**：每次打开 A/B 后缓存 `count=0`，上限随分辨率在 64/96MiB 间切换；
  10 个 A↔B 循环（20 次打开）后 WS 稳定在 ~153MB，没有线性增长。
- **结构上限**：FrameIndex 16B/帧（4573 帧 71.5KiB，2h@30fps 外推 3.46MB）；
  波形 800B/s（2h 5.76MB，硬上限 4h/11.5MB）；预览缓存 32 帧 ~44MB（T2.9.1 未改）；
  截图队列 4 帧；D3D11 纹理/交换链固定。
- `ctest` **20/20**（13.94s，新增 `lapian_frame_cache_test`）；`dist` **32.48MB / 25 文件**。

## 3. 方法

### 3.1 采样口径

`--memory-test` 在应用内用 `GetProcessMemoryInfo`（`PROCESS_MEMORY_COUNTERS_EX`）采样：

| 字段 | 含义 |
|---|---|
| `ws_mb` | `WorkingSetSize`，即 P10/P11 的进程常驻内存 |
| `private_mb` | `PrivateUsage`（private commit），用于区分共享 DLL/堆/解码缓冲 |
| `peak_ws_mb` | `PeakWorkingSetSize`，进程启动以来峰值 |
| `handles` | `GetProcessHandleCount`，观察切文件/索引线程句柄 |
| `cache` | `FrameCacheStateForTest()`：条目/字节/上限/命中/淘汰 |

- P10/P11 结论用 **working set**；private bytes 只做诊断，不替代验收字段。
- 不含 OS 文件缓存；不把 `PrivateUsage` 当成 P10/P11 数字。
- 模式：`empty`（空态）、`pause`（打开→索引就绪→暂停 60s）、`play`（索引就绪→播放 60s）、
  `step`（后退/前进步进，填/命中缓存）、`switch`（A→B 多次切换）。
- 所有模式走产品异步索引路径（不调用 `SetIndexSynchronousForTest`），等
  `IndexReadyForTest()` 后才开始采样，避免把“扫描中”当成稳态。
- 4K 素材 450 帧约 15s 播完；`play` 的 5s/10s 样本是播放中，20s/60s 是播完后保持末帧。
- 本文测量于本机空闲时逐个进程串行执行；没有并行 GUI 回归。

### 5.2 帧缓存与步进

`FrameCache` 只缓存软件帧：硬件帧 `Put` 时用 `av_hwframe_transfer_data` 回拷到
NV12/P010，避免长期持有 D3D11VA 解码表面、把解码器池耗尽；软件帧用
`av_frame_clone` 增加底层 AVBuffer 引用。

| 场景 | 缓存字节 / 条目 | 命中 | p50 | p95 | max |
|---|---:|---:|---:|---:|---:|
| 1080p 200 次后退 | 65,318,400 / 21 | 187/200 | 0.18ms | **32.72ms** | 74.58ms |
| 1080p 200 次前进 | 65,318,400 / 21 | 187/200 | 11.48ms | **46.69ms** | 70.46ms |
| 4K 40 次后退 | 99,532,800 / 8 | 35/40 | 0.60ms | **228.09ms** | 313.61ms |
| 4K 40 次前进 | 99,532,800 / 8 | 35/40 | 141.87ms | **231.68ms** | 248.91ms |

- 1080p 上限 64MiB/24 帧，字节先到上限：`21 × 3,110,400 = 65,318,400B`；
  4K 上限 96MiB/8 帧：`8 × 12,441,600 = 99,532,800B`。
- 1080p 后退 p95 32.72ms、前进 p95 46.69ms，均低于 P7 的 80ms；这是 152s 1080p
  代理、开发机暖解码器、`帧缓存` 已就绪的数字，不是正式 V1 P7。
- 4K 后退/前进 p95 约 228–232ms，未达 P7 的 150ms；4K 的缓存回拷成本和
  “每次从关键帧重解”仍是瓶颈，归 T7.4，不在这里宣称 4K P7 通过。
- 步进期间 WS 高水位：1080p 200 后+200 前 **333.7MB**；4K 40 后+40 前 **593.7MB**。
  这是缓存（65/100MB）+ 解码器/堆高水位，不是 P10/P11 的稳态；P10 的正式口径是
  “打开并暂停 60s”（89.3MB），不含连续步进后的高水位。

### 5.3 切文件释放

`switch` 模式每次打开都走产品路径（旧会话析构、旧索引取消、预览器释放、
`FrameCache` 清空）。3 个 A↔B 循环（6 次打开）：

| 打开 | WS（MB） | private（MB） | cache |
|---|---:|---:|---|
| A（1080p） | 90.3 | 119.9 | 0 |
| B1（4K） | 125.3 | 193.1 | 0 |
| A2（1080p） | 107.4 | 171.5 | 0 |
| B2（4K） | 139.8 | 204.0 | 0 |
| A3（1080p） | 127.6 | 192.5 | 0 |
| B3（4K） | 147.1 | 210.6 | 0 |
| A4（1080p） | 138.9 | 203.0 | 0 |

- 每次切文件后 `cache=count=0`，`max_bytes` 在 64/96MiB 间随分辨率切换。
- 10 个循环（20 次打开）后 WS 稳定在 ~153MB（B 最大 166.3MB），没有线性增长；
  private 稳定在 ~201MB。相对新开 A 的 90MB 有 ~60MB 堆/解码器高水位，但
  没有“每次切文件都涨”的泄漏迹象。
- 高水位仍低于 P10 的 250MB；但这不是“切文件后立刻回到 90MB”的承诺。

### 5.4 结构预算

| 结构 | 上限 / 公式 | 4573 帧 / 2h 外推 | 说明 |
|---|---|---:|---|
| FrameIndex | 16B/帧 + 8B/关键帧 | 4573 帧 **71.5KiB**；2h@30fps 216k 帧 **3.46MB** | `static_assert(sizeof(FrameIndexEntry)==16)` |
| 波形 | 200 bucket/s × 4B | 10min **480KB**；2h **5.76MB**；硬上限 4h **11.5MB** | `kMaxBuckets=2,880,000`，超出忽略 |
| 帧缓存 | 64MiB/24（1080p）；96MiB/8（4K） | 实测 65.3MB / 99.5MB | LRU，字节先到上限 |
| 预览缓存 | 32 帧 ×1280×720 NV12 | **44.2MB** | T2.9.1 原样，未改 |
| 截图队列 | 4 个 pending + 1 个执行中 | 4K 帧引用；PNG 编码临时 | `kMaxQueue=4` |
| 交换链 | 2 个后台缓冲 | 1080p 窗口约 7.4MB；4K 全屏约 66.4MB | `BufferCount=2` |
| 视频纹理 | NV12/P010 单帧 | 1080p 3.1MB / 4K 12.4MB | 随窗口/分辨率重建 |
| 音频 | 150ms 环形缓冲 | 48kHz stereo float 约 57.6KB | 不随片长增长 |
| 索引线程 | 一份 FrameIndex | 2h 约 3.5MB | 取消/切文件 join 后释放 |

### 6.1 为什么普通跳转不写缓存

最初按 ADR-005 的“精确 seek 路径保留帧”实现过 target-only：每次 `GoToFrame`
都把目标帧回拷进缓存。实测：

- 每次普通跳转多一次 1080p 3.1MB 回拷，`--mark-test` 的精确画面 p95 从
  **31.55ms** 抬到 **71.12ms**；
- 连续后退的下一个目标是“当前帧−1”，target-only 缓存里没有，命中率仍为 0。

因此产品路径只在**后退步进**用 `kBackwardWindow` 预热“目标之前一窗帧”，
普通跳转/前进步进/播放走 `kNone`。这是按测量结果收窄策略，不是放弃帧缓存。

## 8. 缺口 / 不宣称

1. **不是基线机**：6C/12T + RTX 4060 + 32GB，明显强于 spec 的 4C/8GB/集显。
2. **不是正式 V1/V4/V10**：1080p 是 152s 代理，4K 是 450 帧代理；P10 的 V1
   是 3–10 分钟真实片，4K P11 应使用 V4。
3. **不是冷 OS 缓存**：没有清 Windows 文件缓存/重启；首次启动/首次打开可能更高。
4. **4K 播放只持续约 15s**：20s/60s 样本是播完保持末帧，不是持续播放 60s。
5. **4K P7 未通过**：p95 约 228–232ms > 150ms；T7.4 处理，不写成 P7 4K 通过。
6. **步进高水位不是 P10/P11 稳态**：1080p 连续步进 333.7MB、4K 593.7MB；
   P10 口径是“打开并暂停 60s”（89.3MB），P11 是播放（106/128.7MB）。
7. **GPU 显存不计入 working set**：D3D11VA 表面在驱动/显存侧；本文只报进程内存，
   不把 GPU 占用当成 P11 已覆盖。
8. **没有 2h soak**：P14 的内存曲线/句柄/线程增长留 T7.3。
9. **没有真实 VFR/HDR/10-bit 4K、200% 真实显示缩放、多显示器、IME**；归 T7.7。
10. 不把本文写成 P10/P11 的正式验收、基线机、正式 V1/V4 或 2h soak 通过。

- 1080p 用 ASCII 硬链接 `build\t7.2-media\test1080.mp4`，避免 PowerShell 5.1
