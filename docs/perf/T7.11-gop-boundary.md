> **2026-10-22 后续（T7.11.1，代码 `7af822e`）：** 本文的 145.60/92.65ms 是
> **修复前**数字。延后回拷修复后：2s GOP p95 **64.13ms**、1s GOP **27.11ms**、
> 1080p60 HEVC 2s **67.31ms**，均过 80；连续后退 p95 0.03/0.06ms。

> 本文是**开发机 + 派生 1s/2s GOP 素材**的专项记录，不是 T7.7 全量验收。
> 目标：spec §4.1 P7「跨 GOP 边界后退专项测：2s GOP 必须 ≤80ms；未达标时
> 该边界条件收紧到 1s」。
> **结论：2s GOP 1080p 未通过（p95 145.60ms）；收紧到 1s GOP 也未通过
> （p95 92.65ms）。根因是后退步进同步回拷 24 帧 FrameCache（76–105ms），
> 解码本身只有 12–42ms。** 不放宽 80ms，不把普通 seek 后单步的 0.06ms
> 当成本专项。

## 2. 口径

- spec §4.1 P7：「±1 帧步进…精确 seek 后紧接 PgUp/PgDn 各测一次。跨 GOP
  边界后退专项测：2s GOP 必须 ≤80ms；未达标时该边界条件收紧到 1s（T2.4 记录）。」
- T7.9 已把「精确 seek 到非关键帧后紧接 PgUp」修到 0.06ms（`kSeekHandoff`
  只保留目标前一帧的 `AVFrame` 引用）。
- 本专项测的是另一种物理路径：**目标帧本身就是关键帧**。`SeekToFrame(K)`
  的 `keyframe == K`，`decode_range(K)` 只解码 K，`index == frame - 1` 不会
  出现，因此没有 handoff 可保留；紧接着 PgUp 到 K-1 时，`kBackwardWindow`
  缓存未命中，必须 seek 回上一个关键帧 P 并解码 P…K-1（整个 GOP），
  同时把最后 24 帧写进 FrameCache（1080p `max_entries=24`）。
  这是 80ms 专项要限制的成本，不能用普通 seek 后单步的 0.06ms 代替。
- GOP 分类：`gop_ms = gop_frames / fps * 1000`；**2s 档 = 1800–2200ms**；
  `>2200ms` 为长 GOP，只列可用档，不参与 80ms 判定；`<1800ms` 为短 GOP
  （1s 收紧档也按 80ms 记录，用于验证 spec 的 fallback 是否有效）。
- 4K 2s GOP 只作诊断（P7 4K 档 150ms），不写 1080p 80ms 通过。

### 5.2 分项：缓存回拷是主因

`LAPIAN_SEEK_LOG=1` 让每个 PgUp 的 `SeekToFrame(K-1)` 打印分项。2s GOP 典型样本：

```text
T7.4 seek_log frame=4379 hit=0 keyframe=4320 decoded=60 seek_ms=0.25
  decode_ms=40.20 cache_ms=104.84 total_ms=145.29 ok=1
```

1s GOP 典型样本：

```text
T7.4 seek_log frame=4349 hit=0 keyframe=4320 decoded=30 seek_ms=0.13
  decode_ms=12.68 cache_ms=75.84 total_ms=88.65 ok=1
```

| 阶段 | 2s GOP（60 帧） | 1s GOP（30 帧） |
|---|---:|---:|
| seek 回关键帧 | 0.25–0.28ms | 0.13–0.17ms |
| 解码 P…K-1 | 36–42ms | 12–14ms |
| **FrameCache 回拷** | **94–105ms** | **76–78ms** |
| 合计 | 136–145ms | 88–92ms |

- 回拷的是 `kBackwardWindow` 的最后 24 帧（1080p `max_entries=24`，64MiB）；
  4K 是 20 帧/256MiB，所以 4K 诊断到 451ms。
- 不含回拷的“seek + 解码 + 呈现”约 **31–48ms**（2s GOP）/ **12–23ms**（1s GOP），
  本来在 80ms 内；**80ms 是被同步回拷推超的**。
- 这与 T7.8 的 step 套件 max 一致：1080p 后退 max 129.82ms、4K 421.92ms
  （`baseline-dev.json`），当时只记为 p95 之外的尖峰；本专项证明它就是
  跨 GOP 边界的第一步成本。
- 因此「收紧到 1s GOP」并不能解决：回拷成本与 GOP 长度基本无关
  （1s 仍 76–78ms），解码只省 20–30ms。

### 5.3 落点

四组的 `frame_ok` 都是 20/20，`CurrentFrameForTest() == keyframe - 1`；
`gop_boundary_plan` 显示 2s 素材 76 个边界、1s 素材 152 个、proxy-V1 仅
2 个（循环取样 20 次）、proxy-V4 7 个（循环取样 20 次）。

## 6. 判定与不宣称

1. **P7 跨 GOP 边界 80ms 未通过**：2s GOP 1080p p95 145.60ms；1s GOP 收紧档
   p95 92.65ms。T7.7 不能写 P7 通过，也不能用 T7.9 的 0.06ms 代替。
2. **不是 T7.7**：V1–V10、F1–F8、P1–P14、基线机、冷缓存都未做。
3. **2s GOP 素材是派生测试片**：`real-gop2s-full.mp4` 来自 T0.3/T2.4，不是
   正式 V1；本专项失败说明**开发机 + 2s GOP 派生素材已超 80ms**，基线机
   只会更差，不需要等基线机才能确认这个缺口。
4. **长 GOP 单列**：proxy-V1 的 10.4s GOP 只作可用档证据，不参与 80ms。
5. **4K 只诊断**：proxy-V4 的 2s GOP 不是正式 V4；451ms 与 T7.4 的
   ~410ms 缓存重填尖峰同源。
6. **不放宽阈值**：不能把 80 改成 145，也不能把“收紧到 1s”写成已通过。
   spec 的 fallback 在当前实现下无效，需要另立性能任务（异步/延后回拷，
   或重新定义边界预算）并走 spec 版本记录；本次只测量与定位。
7. 没有真实 V1/V4、H.265、10-bit/HDR、基线机。
