# T7.11.1 P7 跨 GOP 边界后退：延后回拷（2026-10-22）

> 本文是**开发机 + 派生/合成素材**的专项记录，不是 T7.7 全量验收。
> 目标：修复 T7.11 暴露的 P7 跨 GOP 边界后退缺口，不改 80/150ms 口径。
> **结论：2s GOP 1080p p95 64.13ms、1s GOP 27.11ms、1080p60 HEVC 2s GOP
> 67.31ms，均在 80ms 内；连续后退 p95 0.03ms（2s）/0.06ms（1s），首步单峰
> 97.19ms/1-of-20 超 80。T7.7 仍需基线机与真实 V1 复跑，不能写“P7 全过”。**

## 1. 结论

  ~410ms 缓存重填尖峰同源，仍不达 150ms 诊断档。

## 2. 根因与旧分项口径修正

T7.11 的旧分项把 `total - seek - cache` 记为“解码 36–42ms”，因此得出
“不含回拷 31–48ms”的结论。本次用 `skip_cache=0/1` 对照后发现：

- `cache_ms` 里包含了 `av_hwframe_transfer_data` 的 GPU 队列等待；同步回拷
  24 帧要 76–105ms（首帧 24–25ms + 23×2.7–3.5ms）。
- 真正不预热窗口、只解码整段 GOP 时，2s GOP 总耗时 **58.97ms**
  （decode 58.70ms 均值，51.72–66.36ms），1s GOP **22.63ms**
  （decode 22.44ms，16.34–28.00ms）。
- 旧口径的 36–42ms 是“同步回拷时解码调用看起来很快”，不是无回拷的真实
  端到端耗时。

因此这不是“只差 60ms 回拷”那么简单：同步回拷把 2s 推到 141.78ms；
完全不缓存又会让**连续后退**每一步都重解整段 GOP，2s 实测 p95 92.73ms
（20/20 中 2 个超 80，见 §3.2），仍然过不了 P7。

## 3. 方案比较

### 3.1 采用：1080p 硬解窗口延后回拷

后退窗口命中/未命中逻辑不变，只把“写 FrameCache”从解码循环里挪到呈现之后：

1. 解码到目标帧 K-1 时，窗口内最后 ≤24 帧只做 `av_frame_clone`（硬解帧保留
   D3D11 纹理引用，O(1)，实测 clone 均值 0.012ms）；
2. 目标帧立即交给 `GfxWidget::SetVideoFrame` 呈现并返回；
3. `MainWindow` 用 0ms 定时器在事件循环空闲时按 4 帧/片回拷进 `FrameCache`，
   24 帧约 6 片；实测片均 27.3ms（首帧 ~24ms + 3×2ms），总后台工作
   ≈160ms，不进入 P7 的呈现计时；
4. 回拷完成前，后续 PgUp 直接从待回拷窗口 `clone` 命中（hit=3），连续后退
   仍是毫秒级。

关键约束与处理：

- **解码器表面池**：FFmpeg 的 D3D11VA 静态池默认很小；持 18 帧就报
  `Static surface pool size exceeded`，第一次后退直接解码失败。给 ≤1080p
  硬解设 `extra_hw_frames=32`，4K 不设（避免 20×4K 表面约 250MB）。
- **回拷顺序**：1080p 的 64MiB 预算实际只能放 21 帧（24×3.11MB > 64MiB）。
  必须**从旧帧开始写**；否则 LRU 淘汰的正好是刚写进去的新帧，继续后退会
  每 4 步掉一次窗口。这个 bug 在第一版实现里实测为 step1080 p95 35.65ms、
  4/40 周期 miss；改成旧帧优先后 step1080 p95 0.84ms、2/40 miss。
- **取消/关闭**：切文件、关窗、`InstallIndex`、起播、非后退 seek 都丢弃
  未回拷引用；真正要解码（窗口和 FrameCache 都未命中）前也先释放，避免和
  解码器抢表面。
- **D3D11 上下文**：回拷与截图线程的回读共用立即上下文；`FrameCache::Put`
  现在持 `D3D11ContextMutex` 做 transfer，和 `VideoDecoder`/`SnapshotService`
  同一把递归锁。
- **不缓存命中判断**：目标在 FrameCache 命中时保留剩余待回拷窗口，不能因为
  “不在 pending 里”就取消窗口；否则连续后退会被打断。

### 3.2 否决：短 GOP 完全跳过窗口

先试过更简单的做法：≤2.2s GOP 的 1080p 硬解后退不预热窗口，每步直接解码。
边界专项能过（2s p95 68.58ms、1s 30.59ms），但连续后退 20 步实测：

```text
T7.4 p7_backward n=20 p50_ms=62.01 p95_ms=92.73 max_ms=99.45
  over=2 threshold_ms=80 pass=0
```

原因是紧循环里每一步都要从关键帧重解，GPU 抖动直接吃掉 80ms 余量；长 GOP
更不可能。该方案只保留为诊断对照，不进入产品。

### 3.3 未采用：D3D11 批量 staging 回拷

理论上可以把 24 个 slice 一次 CopySubresourceRegion 到 staging 数组再一次
Map，压低每片首帧的 24ms GPU 同步；但要直接操作解码器纹理数组、自己填
NV12 AVFrame，属于新的 D3D11 路径，风险和验证面都大于本次缺口。当前延后
回拷已把回拷完全移出 P7 计时，暂不需要。

## 4. 实现与代码地图

| 路径 | 改动 |
|---|---|
| `src/media/MediaSession.{h,cpp}` | `PendingCacheFrame` 窗口、`AddPendingCacheFrame` / `CopyPendingCacheFrames` / `CancelPendingCacheWindow`；后退未命中时只 clone，命中 pending 时直接返回；非后退/解码前取消；`seek_log` 增加 `clone_ms` 与 `pending=N` |
| `src/app/MainWindow.{h,cpp}` | `cache_fill_timer_`（0ms，4 帧/片）；后退步进呈现后启动；切文件停止；`FillFrameCacheStep` |
| `src/media/VideoDecoder.cpp` | ≤1080p 硬解 `extra_hw_frames=32`；4K 不加池 |
| `src/media/FrameCache.cpp` | 硬解 transfer 持 `D3D11ContextMutex`（与截图回读串行化） |

后退窗口上限仍是 1080p 64MiB/24 帧、4K 256MiB/20 帧；没有改阈值、基线或
`FrameCache` 预算。

## 6. 口径 / 不宣称

1. **不是 T7.7**：真实 V1–V10、基线机（4C/8GB/集显/SATA SSD/Win11）、冷缓存
   F1-A1、Explorer 真双击仍未做。本文只说明开发机 + 派生/合成素材的专项。
2. **2s GOP 余量只有 15.9ms**（64.13 vs 80）。基线机 iGPU/4 核可能更慢；
   T7.7 必须复跑，不能把本文当 P7 全量通过。
3. **2s 素材是派生的**（`real-gop2s-full` 来自 T0.3/T2.4）；V2 是合成片单
   的 1s GOP 真素材副本；V3 是合成 1080p60 HEVC proxy。都不是正式 V1。
4. **4K 仍诊断**：421.64ms 超 150ms；延后回拷不碰 4K 路径。长 GOP 278.12ms
   只作可用档，不参与 80ms。
5. **`extra_hw_frames=32` 对 ≤1080p 硬解常驻**：多 32 个表面；开发机
   dGPU 的 WS 没有明显上升（P11 114.6MB），但基线机是 iGPU 共享内存，
   T7.7 要记录实际 WS。
6. **P1/P2 仍是热缓存**；不要写成 F1-A1。
7. **没有真实 V4/V5/V8/V10、HDR/10-bit 专项、物理设备丢失**。
