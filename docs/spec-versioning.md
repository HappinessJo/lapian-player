# 文档分层与版本规则

- **版本**：v1.0（2026-10-23）
- **适用**：本项目所有规格、计划、任务、ADR 与交接文档。
- **目的**：v1（本地播放器）已收口，v2（在线拉片）正在进行。避免"v2 的改动写进 v1 冻结文档"或"新 agent 把 v1 文档当成完整品规格"。

## 2. 五条硬规则

1. **delta 只加不改。** `spec-v1.0-delta.md` 只能**新增**条款或**修正 v2 自己的**口径；不得改写 `spec.md` v0.3 的 F1–F8 / P1–P14 语义。
2. **冻结文件只读。** `spec.md`、`tasks.md`、`plan.md` v0.2 不追加 v2 任务或验收；需要修正时，在 delta 里写"对 v0.3 §x.y 的表述修正"，并在 `spec.md` §9 加一行版本记录。
3. **任务分家。** v1 任务台账是 `tasks.md`（已收口，只读）；v2 任务是 `tasks-v2.md`（新文件）。AGENTS 里"任务以 tasks.md 为准"只对 v1 有效，v2 以 `tasks-v2.md` 为准。
4. **ADR 只增不改。** 已接受的 ADR（001–006）不改；新决策开新 ADR（007 起）。ADR-007 目前是**草案**，S3 评审后才算接受。
5. **合并时机。** 当 v2 的功能与验收稳定、且用户决定"以完整品为准"时，才把 v0.3 + delta 合并成 `spec.md` v1.0；在那之前不合并，避免两份基线来回改。

## 4. 常见错误（评审时先检查）

1. **往 `spec.md` 里加"在线模式验收"** → 错。应写进 `spec-v1.0-delta.md`。
2. **往 `tasks.md` 里加 T8.x** → 错。应写进 `tasks-v2.md`。
3. **把 ADR-007 草案当已接受**，或直接在产品里按 D4 开工 → 错。S3 评审通过前它只是建议。
4. **把"完整品"理解成"v1 功能补全"**（例如认为 B 站仍属候选池）→ 错。v2 已把在线模式拉进范围，见 vision。
5. **把 4K/1080P60 写成 MVP 验收项** → 错。普通用户账号不可达，SP2 实测已确认。

---

## 5. 变更流程

- **改 v2 范围/验收**：写 `spec-v1.0-delta.md` → 在 delta 的版本记录加一行 → 同步 `tasks-v2.md`。
- **改 v1 表述（不改语义）**：在 delta 里写"修正 v0.3 §x"→ 在 `spec.md` §9 加一行 → 不动正文条款。
- **推翻已拍板的 5 个决定**：先说明影响哪些验收条款 → 等用户确认 → 改 vision + delta 两边，并记版本。
- **改本文件的层级规则**：升本文件版本 + AGENTS §12 表格里更新版本号。

## 6. 命名约定

- **不重命名** `spec.md` / `plan.md` / `tasks.md`（AGENTS 与大量历史文档引用它们；改名会断链）。
- 增量文件用 `-delta` 后缀；v2 任务用 `tasks-v2.md`；新 ADR 从 `ADR-007` 起编号。
- 交接文档按日期：`docs/handoff-YYYY-MM-DD-<scope>.md`。
- 性能/测量记录放 `docs/perf/`，命名与被测任务对应。
